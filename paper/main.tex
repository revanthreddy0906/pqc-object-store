\begin{abstract}
Ciphertext stored in cloud object stores today can be decrypted once a large quantum computer
exists, so storage is an early candidate for migration to ML-KEM (FIPS~203). The cost of
ML-KEM has been measured for isolated primitives and for TLS connections, where one key
establishment serves a whole session, but not in client-side envelope encryption, where every
object needs its own. We present a reproducible, instrumented evaluation of per-object
post-quantum key establishment in concurrent S3-compatible storage workloads. One client data
path (Python, liboqs, chunked AES-256-GCM) is run against a single-node MinIO server on AWS with
ML-KEM-768, X25519, RSA-OAEP-4096, a symmetric-only baseline, plaintext, two X25519+ML-KEM-768
hybrids (one of them X-Wing) and a bounded-session variant, in an exploratory campaign
(\TotalRuns{} runs) and a pre-registered confirmatory campaign on x86 and ARM clients
(\RevAllRuns{} runs, \RevAllRequests{} million requests, no failed request). ML-KEM-768 takes
\RevKeMLKEMPut\,ms per PUT and \RevKeMLKEMGet\,ms per GET on the x86 client. In paired
equivalence tests with a $\pm$5\,\% margin and Holm correction, its throughput is equivalent to
X25519 in \RevPrimaryEq{} of 8 pre-specified cells on each architecture and inconclusive in the
remaining \RevPrimaryInc; where the client CPU is the bottleneck it is \RevHotDeficit--\ArmHotDeficit\,\%
slower, and X-Wing \RevXwingHotDeficit--\ArmXwingHotDeficit\,\% slower. RSA-4096 limits
small-object reads to \RevRsaGetLo--\RevRsaGetHi{} of ML-KEM's throughput. The lasting cost of
ML-KEM is \RevMetaExtraMLKEM{} bytes of metadata per object. Bounded sessions remove
\RevSessCpuSavingLo--\RevSessCpuSavingHi\,\% of client CPU per request and change throughput only
where the client is the bottleneck, at the price of up to $B_{\max}$ objects per leaked root.
Response time degrades at \RevQSmallRhoLastStable--\RevQMidRhoFirstUnstable{} of peak
throughput; a state-dependent queueing
model halves the prediction error of M/M/c but still places the knee too high. All findings are
limited to this client stack, a single-node store and one cloud region.
\end{abstract}

\section{Introduction}
Cloud object stores keep data for years, and much of that data is encrypted under keys
established with RSA or elliptic-curve Diffie--Hellman. Shor's algorithm would allow a
sufficiently large quantum computer to recover those keys, so an adversary who records
ciphertext today can decrypt it once such a machine exists, a threat usually called
``harvest now, decrypt later''. For data at rest the exposure lasts as long as the data is
retained. In August 2024 NIST published FIPS~203, standardizing the module-lattice
key-encapsulation mechanism ML-KEM~\cite{fips203}.

With client-side envelope encryption, as implemented by the Amazon S3 Encryption Client and by
Azure Blob Storage client libraries~\cite{s3ec,azurecse}, every object is encrypted under its own
data key, and that key is protected for the recipient and stored with the object. Replacing the
key protection with ML-KEM therefore places a key establishment, and its 1{,}088-byte
ciphertext, on every PUT and every GET rather than once per connection.

\textbf{What is known.} Primitive-level studies report the cost of key generation, encapsulation
and decapsulation and the sizes of keys and ciphertexts on several processor
families~\cite{liboqs,rodriguez2025,demir2025,lopez2025}. Studies of post-quantum TLS and KEMTLS
measure connection establishment under latency, loss and bandwidth limits
\cite{paquin2020,sikeridis2020,sosnowski2023,giron2023}. Storage studies measure the S3 interface
without cryptography~\cite{gadban2021} and client-side encryption without post-quantum key
establishment~\cite{henziger2019,ozeri2023}.

\textbf{What is not known.} None of these measures ML-KEM where an object store would use it: once
per object, on a data path whose throughput is set jointly by client CPU, network, metadata
handling and the storage server, with many clients at once. Whether per-object ML-KEM changes
capacity, where the bottleneck lies, when amortizing it is worthwhile and whether a queueing model
predicts the point of degradation are open questions
(Section~\ref{sec:related}, Table~\ref{tab:gap}).

\textbf{Thesis.} This paper presents a reproducible systems-level evaluation of post-quantum
per-object key establishment in concurrent S3-compatible storage workloads, complemented by
bounded key-establishment amortization and queue-aware capacity analysis. Its contributions are,
in order of importance:
\begin{itemize}
\item[\textbf{C1}] \textbf{End-to-end benchmark.} An instrumented client-side envelope-encryption
path on which ML-KEM-768, X25519, RSA-OAEP-4096, symmetric-only, plaintext and two hybrid modes
are interchangeable, so that differences isolate key establishment
(Sections~\ref{sec:design} and~\ref{sec:impl}).
\item[\textbf{C2}] \textbf{Systems evidence.} Measurements over object size, 1--500 concurrent
workers, closed and open loop, two client architectures, throughput, latency, CPU, memory and
metadata, with the independently restarted run as the experimental unit and pre-registered
paired equivalence tests (Sections~\ref{sec:method} and~\ref{sec:results}).
\item[\textbf{C3}] \textbf{Security--performance mechanism.} Bounded session amortization of
ML-KEM with object and time limits, reported as performance gained against objects and bytes
exposed per root (Section~\ref{sec:tradeoff}).
\item[\textbf{C4}] \textbf{Capacity analysis.} Open-loop measurements that locate the
response-time knee, and a comparison of M/M/c with state- and load-dependent models on held-out
load points (Section~\ref{sec:queue}).
\end{itemize}
The architecture and commit protocol support C1; we do not claim them as a new cryptographic
construction (Table~\ref{tab:claims}).

\textbf{Research questions.} \textbf{RQ1:} What does per-object ML-KEM-768 add to latency,
throughput, CPU, memory and metadata, compared with RSA-4096, X25519 and symmetric-only baselines
on the same data path? \textbf{RQ2:} How does this change with object size, with 1--500 workers
and with a hybrid construction? \textbf{RQ3:} Where does response time degrade under open-loop
load, can a queueing model predict that point, and what does bounded amortization buy at what
exposure?

\textbf{Findings.} In the evaluated configuration:
(i) per-object ML-KEM-768 takes \RevKeMLKEMPut--\RevKeMLKEMGet\,ms on the x86 client and
\ArmKeMLKEMPut--\ArmKeMLKEMGet\,ms on the ARM client, less than X25519 on PUT;
(ii) its throughput is equivalent to X25519 within $\pm$5\,\% in \RevPrimaryEq{} of 8
pre-specified cells on each architecture, the other \RevPrimaryInc{} being inconclusive, and it
is measurably slower (\RevHotDeficit--\ArmHotDeficit\,\%) only where the client CPU is the
bottleneck;
(iii) X-Wing costs about \RevXwingOverMlkemGet--\RevXwingOverMlkemPut{} times the
key-establishment time of ML-KEM alone and is
\RevXwingHotDeficit--\ArmXwingHotDeficit\,\% slower than X25519 in that same client-bound cell,
and equivalent from 1\,MiB upward;
(iv) RSA-4096 is the one mode that moves the bottleneck;
(v) the small-object write ceiling lies in the storage server's metadata path, not in its disk;
(vi) sessions save a few percent of client CPU and nothing else unless the client is saturated;
and (vii) the response-time knee lies at \RevQSmallRhoLastStable--\RevQMidRhoFirstUnstable{} of
peak throughput.

\textbf{Scope.} We do not evaluate the security of ML-KEM, side channels, or transport security,
which is held constant. All performance statements concern one Python client stack, one
single-node MinIO deployment and one cloud provider (Section~\ref{sec:validity}).

\section{Background}\label{sec:background}
\subsection{Key-Encapsulation Mechanisms and ML-KEM}
A key-encapsulation mechanism (KEM) consists of key generation, encapsulation, which takes the
recipient's public key and outputs a ciphertext and a shared secret, and decapsulation, which
recovers the secret with the private key. ML-KEM, derived from CRYSTALS-Kyber, relies on the
hardness of module learning with errors. ML-KEM-768 targets NIST security category~3 with a
1{,}184-byte encapsulation key, a 1{,}088-byte ciphertext and a 32-byte shared
secret~\cite{fips203}. Decapsulation uses \emph{implicit rejection}: a modified ciphertext yields
a pseudorandom secret instead of an error, so tampering is detected by the authenticated
encryption that follows.

\subsection{Hybrid KEMs}
A hybrid KEM combines a classical and a post-quantum component so that the result stays secure
while either remains unbroken. The combiner matters: X-Wing~\cite{barbosa2024,xwing} combines
X25519 with ML-KEM-768 as
$\mathrm{SHA3\mbox{-}256}(ss_M\|ss_X\|ct_X\|pk_X\|\mathit{label})$ and derives both private keys
from one 32-byte seed; its security proof depends on these concrete choices and does not carry
over to other ways of mixing two secrets.

\subsection{Envelope Encryption and Object Storage}
In envelope encryption a per-object data key encrypts the object, and key establishment protects
that key. We derive data keys with HKDF-SHA256~\cite{rfc5869} and encrypt with AES-256-GCM, whose
security requires that a nonce is never reused under one key~\cite{sp80038d}. The classical
alternatives are key transport with RSA-OAEP~\cite{rfc8017} and ephemeral-static X25519
\cite{rfc7748}. Object stores expose buckets and keys through HTTP operations, chiefly PUT and
GET of whole objects; the S3 interface is the de facto standard~\cite{gadban2021}. We use
MinIO~\cite{minio}, compiled from its final community release (\MinioRelease).

\subsection{Queueing Models}
An M/M/c queue has Poisson arrivals at rate $\lambda$, $c$ servers and exponential service times
with mean $S$~\cite{harchol2013}. With $a=\lambda S$ the mean response time is
$W=S+C(c,a)\,S/(c-a)$, where $C$ is the Erlang~C probability of waiting. Its service time does
not depend on load. A \emph{state-dependent} birth--death queue lets the total service rate
$\mu(n)$ depend on the number $n$ of requests in the system; its stationary distribution is
$p_n\propto\prod_{k\le n}\lambda/\mu(k)$ and its mean response time follows from Little's law.

\textbf{Primitive benchmarks.} Library benchmarks~\cite{liboqs} and comparative studies
\cite{rodriguez2025,demir2025,lopez2025} quantify the three KEM operations and the larger keys
and ciphertexts, including on ARM and constrained devices. They establish that platform and
implementation matter, which is why we repeat our primary comparison on a second architecture,
but they contain no storage, concurrency or end-to-end request latency.

\textbf{Post-quantum TLS and KEMTLS.} Paquin et al.~\cite{paquin2020} measure hybrid key exchange
and post-quantum signatures in TLS~1.3 under emulated latency and loss, and Sikeridis et
al.~\cite{sikeridis2020} study post-quantum authentication and its effect on server throughput.
Sosnowski et al.~\cite{sosnowski2023} add a white-box decomposition of the TLS~1.3 handshake, and
Giron et al.~\cite{giron2023} evaluate hybrid KEMTLS in simulated and geographically separated
networks. These are the closest systems precedents, but their amortization boundary differs: a
handshake protects a connection, whereas in client-side object encryption key establishment and
its ciphertext recur for each object.

\textbf{Storage.} Gadban and Kunkel~\cite{gadban2021} analyze the S3 interface for HPC workloads
and attribute losses to layers of the client stack; our harness applies the same separation to
cryptographic stages. Henziger and Carlsson~\cite{henziger2019} study how client-side encryption
affects delta encoding in file synchronization, and Ozeri et al.~\cite{ozeri2023} argue for
placing encryption at the storage client. None involves post-quantum key establishment.

\textbf{Post-quantum cloud storage.} Prikutse et al.~\cite{prikutse2026} combine AES-256-GCM,
X25519+ML-KEM-768 and ML-DSA-65 for multi-file cloud storage and amortize signatures over a batch
by commitment. According to its abstract, its evaluation concerns the signing phase, not
concurrent S3 PUT/GET, queueing or a comparison with classical per-object key establishment.
Junaid~\cite{junaid2026} proposes a client-side hybrid post-quantum encryption architecture with
self-hosted key management; its abstract reports per-operation latency on a microcontroller and a
server, not an object-store workload under concurrent clients.

\textbf{Bounded key reuse.} Amazon S3 Bucket Keys derive per-object data keys from a time-limited
bucket-level key and reduce key-service requests by up to 99\,\%~\cite{s3bucketkeys}; the AWS
Encryption SDK caches data keys under age, message and byte limits~\cite{esdkcache}. Our session
mode applies this established principle to ML-KEM roots and quantifies the trade-off.

\textbf{Search.} In October 2026 we ran keyword searches, restricted to arXiv, dblp and Semantic
Scholar and on the open web, combining \emph{ML-KEM}, \emph{Kyber} or \emph{X-Wing} with
\emph{object storage}, \emph{S3}, \emph{MinIO}, \emph{client-side encryption}, \emph{envelope
encryption} and \emph{concurrency}; the queries and their outcome are logged in the artifact.
This is a keyword search, not a systematic review. It returned primitive benchmarks, transport
studies, vendor tutorials and the two storage designs above, but, to our knowledge, no measurement
of per-object ML-KEM under concurrent S3 load.

\section{System and Threat Model}\label{sec:design}
\subsection{Threat Model}
The network and the object store are honest-but-curious for confidentiality and potentially
malicious for integrity: an adversary may read, replace, delete, reorder or replay stored
ciphertexts and manifests. The adversary does not hold the recipient's decapsulation key and may
in the future operate a quantum computer. Availability, traffic analysis, deletion of whole
objects, compromised endpoints and side channels in the client are out of scope.

\subsection{Key-Establishment Modes}
Table~\ref{tab:modes} lists the modes. All encrypting modes share the HKDF and chunked AES-GCM
path, so differences between them isolate key establishment. B0 stores plaintext through the same
framing; B1 derives keys from a pre-shared 32-byte key and is the symmetric-only floor; R1
transports a random secret with RSA-OAEP-4096; B2 uses ephemeral-static X25519; P1 uses
ML-KEM-768. Two hybrids combine X25519 with ML-KEM-768. \emph{P3 is X-Wing} as specified in
\cite{xwing}: we implement its key derivation from a 32-byte seed, its SHA3-256 combiner and its
ciphertext layout, and verify key generation, encapsulation and decapsulation against the
draft's published test vectors. \emph{P2 is a study-specific concatenation hybrid}: it stores the
ML-KEM ciphertext followed by the X25519 ephemeral key and feeds both 32-byte secrets,
concatenated, to HKDF together with the object context. P2 predates our X-Wing implementation; we
keep it as a performance reference and make no security claim for its combiner. N1 amortizes one
ML-KEM encapsulation over a bounded session (Section~\ref{sec:n1design}). A reader must name the
mode it expects, so a planted plaintext object cannot downgrade an encrypted one.

\subsection{Per-Object Envelope and Commit Protocol}
Algorithm~\ref{alg:putget} shows PUT and GET for mode P1. An object is identified by
$I=(\mathit{tenant},\mathit{bucket},\mathit{key},\mathit{version})$, where versions are
time-ordered UUIDv7 values. The context $\mathit{ctx}$ is canonical JSON of $I$, the mode, the
algorithm names, chunk size and count, plaintext size, recipient key identifier and the SHA-256
hash of the key-establishment ciphertext $C$; it is bound into the data key and into every chunk.
Objects are split into 4\,MiB chunks, and chunk $j$ is encrypted with nonce
$p\|\mathrm{be}_{64}(j)$ under a random 32-bit prefix $p$ and associated data
$\mathit{ctx}\|j\|\ell_j\|\mathit{final}_j$, so deletion, reordering, truncation, extension and
cross-object splicing of chunks fail authentication. Each version is stored under
\texttt{key.pqcs/version/} as a ciphertext stream \texttt{data.enc} and a manifest
\texttt{manifest.json} holding $\mathit{ctx}$, $C$, the salt and the prefix. The manifest is
written last and serves as the commit record: readers only consider versions whose manifest
exists, so an interrupted upload is never visible. One logical PUT is therefore two S3 writes.

\begin{algorithm}[t]
\caption{Per-object PUT and GET (mode P1)}
\label{alg:putget}
\footnotesize
\begin{algorithmic}[1]
\Procedure{Put}{$\mathit{key}, M, ek$}
\State $v \gets \textsc{UUIDv7}()$; \ $I \gets (\mathit{tenant},\mathit{bucket},\mathit{key},v)$
\State $(C,S) \gets \mathrm{ML\mbox{-}KEM.Encaps}(ek)$
\State $\mathit{salt} \xleftarrow{\$} \{0,1\}^{256}$; \ $p \xleftarrow{\$} \{0,1\}^{32}$
\State $\mathit{ctx} \gets \textsc{Canon}(I,\text{mode},n,|M|,\mathrm{id}(ek),\mathrm{H}(C),\dots)$
\State $K \gets \mathrm{HKDF}(S,\mathit{salt},\text{``pqc-s3-object-v2''}\|0\|\mathit{ctx})$
\For{$j \gets 0$ \textbf{to} $n-1$} \Comment{streamed in 8\,MiB parts}
\State $c_j \gets \mathrm{AES\mbox{-}GCM}_K(p\|\mathrm{be}_{64}(j), M_j, \mathit{ctx}\|j\|\ell_j\|\mathit{final}_j)$
\EndFor
\State write $c_0\|\dots\|c_{n-1}$ to \texttt{key.pqcs/$v$/data.enc}
\State commit: write $(\mathit{ctx},C,\mathit{salt},p)$ to \texttt{key.pqcs/$v$/manifest.json}
\EndProcedure
\Procedure{Get}{$\mathit{key}, dk, \text{mode}$}
\State $v \gets$ newest version with a manifest; read and parse it
\State \textbf{reject} unless identity, mode, key id and $\mathrm{H}(C)$ all match
\State $S \gets \mathrm{ML\mbox{-}KEM.Decaps}(dk,C)$; \ $K \gets \mathrm{HKDF}(S,\mathit{salt},\dots)$
\For{each chunk $c_j$ of \texttt{data.enc}}
\State $M_j \gets \mathrm{AES\mbox{-}GCM}^{-1}_K(\dots)$; \ \textbf{reject} on failure
\EndFor
\State \textbf{reject} unless exactly $n$ chunks were read and the last is final
\EndProcedure
\end{algorithmic}
\end{algorithm}

\subsection{Bounded Sessions (Mode N1)}\label{sec:n1design}
In N1 one encapsulation yields a root $S_r$, and object $i$ of the session uses
\[K_i=\mathrm{HKDF}(S_r,\mathit{salt}_i,\text{``pqc-s3-session-v1''}\|0\|\mathit{ctx}_i),\]
with the session identifier, the object's sequence number and the bound authenticated in
$\mathit{ctx}_i$. Every object still stores the session's ML-KEM ciphertext, so it can be
decrypted alone. A root protects at most $B_{\max}$ objects and lives at most $T_{\max}$ seconds,
whichever is reached first. In a queue-aware variant the object bound of each new session is
\[B_t=\mathrm{clip}\bigl(B_{\min},B_{\max},\mathrm{round}(B_{\min}+(B_{\max}-B_{\min})\hat\rho)\bigr),\]
where $\hat\rho$ is a moving average ($\alpha=0.2$) of the fraction of a client process's worker
threads with a request in flight. Receivers cache decapsulated roots under their own caps and
reject objects whose authenticated sequence number exceeds them.

\subsection{Cryptographic Core}
ML-KEM-768 comes from liboqs~\LiboqsVersion{} through liboqs-python~\LiboqsPyVersion{}
\cite{liboqs,liboqspython}. We build liboqs from a pinned release with only the ML-KEM parameter
sets enabled and load it from an explicit installation path, so the benchmark cannot silently pick up a different library; a start-up check verifies the library version and that ML-KEM-768 is enabled, and every call checks key and ciphertext sizes.
RSA-OAEP-4096 (SHA-256), X25519, HKDF and AES-256-GCM come from
pyca/cryptography~\CryptographyVersion{}~\cite{pyca}. A registry maps each mode to its
key-establishment and recovery functions, and the envelope module turns the result into a
streaming chunk encryptor or decryptor, so the storage code never holds a whole object. Before
any timed operation every worker process runs a warm-up that loads the libraries, performs a key generation, encapsulation, decapsulation, derivation and encryption round trip, and one full round trip in the mode under test, so that one-off costs never enter a timer.
An interoperability test checks ML-KEM in both directions against an independent implementation
(OpenSSL through pyca), and the manifest parser rejects unknown or missing fields, wrong types, inconsistent sizes and a key-establishment ciphertext that does not match its hash.

X-Wing uses the same liboqs build for its ML-KEM component, through the library's derandomized
key-generation and encapsulation functions, and the same X25519 as mode B2, so a difference
between P3 and P1 or B2 reflects the construction and not a different library. The expanded
decapsulation key is cached per process, which the draft permits; P1 likewise holds its expanded
key.

\subsection{Storage Layer}
The storage layer implements the commit protocol of Algorithm~\ref{alg:putget} on the MinIO
Python SDK~\MinioPyVersion. Ciphertext records are passed to the SDK through a file-like adapter
over the encryptor's output, so an object is uploaded in 8\,MiB parts while it is being encrypted;
on GET the stream is decrypted chunk by chunk into a sink. For benchmarking, the HTTP client uses a connection pool sized to the worker threads and performs no automatic retries, so failures are counted rather
than hidden inside latency. Auxiliary functions list committed versions, verify a commit by reading
it back, delete versions and collect uncommitted data left behind by interrupted uploads.

\subsection{Measurement Harness}
A \emph{run} executes one configuration (mode, operation, object size, concurrency and loop type)
with freshly started worker processes; it is the unit of replication. Concurrency $N$ is realized
as exactly $N$ worker threads spread over $\min(N,16)$ processes, one per vCPU. Each process warms
up, reports readiness, and all of them start at a common wall-clock instant, so that no worker
measures while others are still starting. Each run has a 5\,s warm-up phase and a 20\,s measured
phase; Python's garbage collector is run before and disabled during the timed window, so its
pauses cannot land inside a stage timer. In closed-loop runs each thread issues requests back to
back. In open-loop runs each process draws Poisson arrivals at its share of the target rate, a
request waits in a queue for a free thread, and the wait is recorded separately; a request that
cannot start before the end of the run is recorded as a failure, never dropped. GET runs read a
set of pre-written fixture objects that are created before and deleted after the run, and every
object written by a PUT run is deleted afterwards, outside the timed window.

Every request, including warm-up requests and failures, produces one record with
\texttt{perf\_counter} timers for the five stages of Algorithm~\ref{alg:putget}---key
establishment, key derivation, AES-GCM, manifest handling and storage---its total latency, the
thread CPU time it consumed, bytes on the wire and metadata size, plus identifiers that tie it to
its run, repetition, code commit and configuration. A client sampler records the CPU time and
resident memory of the worker processes and the host's CPU and network counters once per second;
a server sampler reads the same information from MinIO's Prometheus metrics endpoint.
A server sampler reads MinIO's Prometheus endpoint and, in the confirmatory campaign, a
node-exporter endpoint on the server host that supplies dirty and write-back memory, disk
write rate and latency, and I/O wait.

\subsection{Validation}
A validator checks every data set before analysis and refuses it if any check fails: checksums of
all files; a complete schema with correct types for every record; that no request's stage times
exceed its total; that per run the 99th percentile of unaccounted time stays below 2\,\% of the
request time and below 1\,\% in aggregate; and that no N1 session exceeds its bound. The
\TestCount{} automated tests cover the cryptographic core, the commit protocol, tampering (bit flips; deleted, reordered, duplicated, truncated or extended chunks; swapped, replayed or relabelled manifests; mode downgrade), that manifests contain no secret material and private-key files are protected, session bounds under concurrent stress, and
end-to-end runs against a live MinIO.

\subsection{Testbed Automation}
A single script provisions and operates the cloud testbed: it creates both instances in one
cluster placement group with a firewall that admits SSH only from the operator's address, copies
the committed code, builds MinIO from source into a Docker image, formats the server's local NVMe
disk at boot, runs network (iperf3, ping) and disk (fio) baselines, starts experiments in a
detached session, fetches results and stops or deletes all resources. Before launch, a planner
estimates the run time and cost of each experiment configuration. To bound cost, both instances
stop themselves when idle, and the client stops itself shortly after an experiment completes.

\subsection{Analysis Pipeline}
A summarizer streams the compressed request records of each experiment once and writes one row
per run. A statistics stage computes intervals, paired equivalence tests, bottleneck labels and
the queueing models. A final stage generates every figure, table and number in this paper as
\LaTeX{} macros, so no result is typed by hand.

\section{Experimental Methodology}\label{sec:method}
\subsection{Two Campaigns}

\subsection{Testbeds}
In every testbed the client and MinIO run on two instances in one cluster placement group; MinIO
is a single node in Docker with host networking on an \ServerType{} instance (16 vCPU, local
NVMe, XFS). The exploratory campaign ran in AWS region \Region{} with a \ClientType{} client
(\ClientCPU, \ClientVCPU{} vCPU, \ClientRAMGiB\,GiB): \LinkGbit\,Gbit/s between the hosts,
\RTTms\,ms round trip, \FioReadMiB/\FioWriteMiB\,MiB/s disk read/write. The confirmatory campaign
ran in region \RevRegion, on a different account: first with the same instance types
(\RevClientCPU; \RevLinkGbit\,Gbit/s, \RevRtt\,ms, \RevDiskRead/\RevDiskWrite\,MiB/s), then with a
c7g.4xlarge client (\ArmClientCPU, 16 vCPU) and a new server of the same type
(\ArmLinkGbit\,Gbit/s, \ArmRtt\,ms, \ArmDiskRead/\ArmDiskWrite\,MiB/s). Because the ARM testbed
has a different server instance and network path, we compare ratios between modes across
architectures, never absolute throughput.

\subsection{Workload}
PUT and GET are measured separately, mostly in a closed loop. Each run has a 5\,s warm-up and a
20\,s measured phase. The exploratory campaign measures concurrency 1--500 at 64\,KiB and
1\,MiB (16\,MiB up to 128 workers) and object size 1\,KiB--500\,MiB at one worker. The
confirmatory campaign measures the primary cells defined below; a hybrid matrix of 1\,KiB to
128\,MiB at 1 and 128 workers; sessions at $B_{\max}\in\{1,10,100,1000\}$ and
$T_{\max}\in\{1,10,60\}$\,s; and, for the queueing analysis, closed-loop throughput at 1--256
workers and Poisson arrivals at 12 rates from 1{,}500 to 5{,}600 requests/s served by 256
threads, for 1\,KiB and 64\,KiB PUT.

\subsection{Metrics}
\begin{itemize}
\item \emph{Per-object key-establishment time}: the time a request spends in encapsulation, RSA
unwrapping, Diffie--Hellman or decapsulation, from the stage timers. The study's assignment calls
this metric ``handshake overhead''; we avoid that name because no multi-message protocol is
involved.
\item \emph{Throughput}: successful requests, or MiB, per second of the measured window.
\item \emph{CPU}: CPU of the client's benchmark processes and of MinIO during the measured
window, and client thread CPU time per request.
\item \emph{Memory}: peak resident memory and its growth over the run.
\item \emph{Response time} (open loop): queue wait plus service time per request.
\item \emph{Metadata}: bytes of the manifest stored with each object.
\end{itemize}
Above one worker, stage timers include time spent waiting for the Python interpreter lock, so
key-establishment time and stage shares are reported at one worker only.

\subsection{Experimental Unit and Replication}
A run starts fresh worker processes and is the experimental unit. The millions of requests inside
a run sharpen that run's own estimate; they are not independent replicates, and no interval in
this paper is computed over requests. Runs are organized in randomized complete blocks: one
repetition contains every mode of a cell once, in shuffled order, and modes are compared only
within a repetition.

Between runs the harness waits until the server host's dirty plus write-back memory is below
32\,MiB and its disk write rate below 5\,MiB/s for two consecutive seconds, at most 40\,s. In the
exploratory batches A--C this pause had silently fallen back to 5\,s, which slowed some PUT runs
that followed another PUT run by \StallSlowMin--\StallSlowMax\,\%; batch D repeated the affected
cells with a fixed 40\,s pause. In the confirmatory campaign the measured pause had a median of
\RevSettleMedian\,s.

\subsection{Equivalence Testing}\label{sec:tost}
For a cell and two modes $a$ and $b$, repetition $i$ gives the paired log ratio
$d_i=\log(x_{a,i}/x_{b,i})$ of throughput. We test equivalence with two one-sided tests
(TOST)~\cite{schuirmann1987,dixon2018} against the bounds $[\log 0.95,\log 1.05]$:
\[H_0^{-}:\ \mathrm{E}[d]\le\log 0.95,\qquad H_0^{+}:\ \mathrm{E}[d]\ge\log 1.05,\]
each with a one-sided paired $t$-test at $\alpha=0.05$. The modes are declared \emph{equivalent}
only if both are rejected, which is the same as the 90\,\% confidence interval of the ratio lying
inside $[0.95,1.05]$; the TOST $p$-value is the larger of the two. We also show the 95\,\%
interval for estimation. A cell whose 90\,\% interval lies wholly outside the bounds is
\emph{non-equivalent}; anything else is \emph{inconclusive}, which is not evidence of ``no
difference''.

\textbf{Margin.} Five percent is our smallest effect of interest, fixed in advance: it is below a
capacity change that would alter provisioning, below the \BatchDriftPct\,\% drift in absolute
small-object throughput observed between sessions of the exploratory campaign, and it is the
margin that campaign already used. We report sensitivity at $\pm$2\,\% and $\pm$10\,\%.

\textbf{Primary family and multiplicity.} The confirmatory hypothesis is the ratio P1/B2 in eight
closed-loop cells chosen before the campaign: 64\,KiB GET at 128 and 500 workers; 64\,KiB PUT at
32 workers (the knee of the throughput curve) and 128; 1\,MiB PUT and GET at 32; and 16\,MiB PUT
and GET at 32. The eight $p$-values are adjusted with Holm's procedure~\cite{holm1979}, which
controls the family-wise error rate. The same family measured on the ARM client is a replication
and is adjusted in the same way. All other comparisons (P3 and P2 against P1 and B2, R1 against
P1, and every cell outside the family) are exploratory and reported with unadjusted intervals.

\textbf{Power.} From the paired log-ratio standard deviations of the exploratory campaign, a
normal-approximation calculation at $\alpha=0.05/8$ and power 0.8 required at most 7 repetitions
in every primary cell except the knee, which required about 19. We therefore ran 10 repetitions
per cell and 20 at the knee, with no optional stopping.

\textbf{Stall rule.} Fixed in advance and blind to the mode: a closed-loop run is a \emph{stall}
if its server CPU is below 0.8 times and its throughput below 0.9 times the median of its own
cell. The primary analysis uses all runs; excluding stalls is a sensitivity analysis.

\subsection{Queueing Protocol}\label{sec:qprotocol}
The 12 open-loop rates are sorted; the 1st, 3rd, \ldots{} are training points and the 2nd, 4th,
\ldots{} are held out. Models may use training points and the closed-loop runs, and are scored by
mean absolute percentage error (MAPE) on the held-out rates at which the system was stable. A
rate is stable if every run delivers at least 97\,\% of the offered rate with a mean queue wait
below 10\,ms; response times of unstable runs grow with run length and are lower bounds.

\subsection{Deviations from the Pre-Registration}
(1) The first attempt at batch E was cut off after 134 of 300 runs when an account-level spending
guard stopped both instances. Its data was never downloaded or analysed; the batch was restarted
from its first run with the same configuration and seed. (2) The profiling batch was run twice,
once under system-call tracing and once under CPU sampling, because the first CPU profiles were
unusable. (3) The stall rule is applied to closed-loop runs only, since open-loop throughput is
fixed by the offered rate.

\textbf{Not pre-specified.} The pre-registration fixed the primary family, its test and the
training and held-out split. It did not fix the following, which were chosen during analysis and
are exploratory: applying Holm's correction to the ARM family as well; the definition of the knee
as twice the light-load response time; the functional form of the load-dependent model; the
order-and-time regression of Section~\ref{sec:validity}; and the layout of the session and hybrid
tables.

\subsection{ML-KEM against X25519 (Confirmatory)}\label{sec:primary}
Table~\ref{tab:tost} and Fig.~\ref{fig:tost} give the pre-registered result. On the x86 client

\emph{Large objects.} All four cells at 1\,MiB and 16\,MiB are equivalent on both architectures,
with ratios between \RevLargeRatioLo{} and \RevLargeRatioHi{} on x86 and between
\ArmLargeRatioLo{} and \ArmLargeRatioHi{} on ARM. Here the network or the server sets the pace.

\emph{A real difference where the client is the bottleneck.} At 64\,KiB GET with 500 workers

interval touches the bound and the verdict is inconclusive, and in neither case does it pass at
$\pm$2\,\%. At 128 workers the same workload shows no difference.

\emph{Noise, not difference, in small PUT.} The two 64\,KiB PUT cells have ratios near 1
(\RevNoisyRatio{} and \RevKneeRatio{} on x86) but paired standard deviations of
\RevKneeSd--\ArmNoisySd\,\% in log ratio, the server-side variation described in
Section~\ref{sec:bottleneck}. The knee cell passes on its own on x86 ($p=\RevKneeP$) but not after
correction ($p_{\text{Holm}}=\RevKneePHolm$), and passes after correction on ARM. The cell at 128
workers is inconclusive on both: at its observed standard deviation ten repetitions give a single
test a power of only \RevPowerNoisy\,\%, and about \RevPowerNoisyNeeded{} would be needed for

\subsection{Queueing Behaviour (RQ3)}\label{sec:queue}
\textbf{Where the knee is.} Under Poisson arrivals of ML-KEM PUTs (batch H), 1\,KiB requests are
stable up to \RevQSmallLastStable{} requests/s and unstable from \RevQSmallFirstUnstable; 64\,KiB
requests are stable up to \RevQMidLastStable{} and unstable from \RevQMidFirstUnstable. Against
the peak closed-loop throughput of the same batch (\RevQSmallPeak{} and \RevQMidPeak{}
requests/s) the transition lies between $\rho=\RevQSmallRhoLastStable$ and
\RevQSmallRhoFirstUnstable{} at 1\,KiB and between \RevQMidRhoLastStable{} and
\RevQMidRhoFirstUnstable{} at 64\,KiB. Mean response time doubles, relative to light load, between
\RevQSmallKneeLo{} and \RevQSmallKneeHi{} requests/s at 1\,KiB and between \RevQMidKneeLo{} and
\RevQMidKneeHi{} at 64\,KiB. The exploratory campaign found the knee in the same place for the
symmetric-only mode B1 and for P1, so it is a property of the store, not of the key
establishment.

\textbf{Models.} We compare three models (Fig.~\ref{fig:queuerev}, Table~\ref{tab:queue}).
(a)~M/M/$c$ with the light-load service time $S_0$, capacity $\mu$ from the two most overloaded
training rates and $c=\mathrm{round}(\mu S_0)$. (b)~A state-dependent queue whose service rate
$\mu(n)$ is the closed-loop throughput measured with $n$ workers, interpolated linearly; it uses
no open-loop data at all. (c)~A load-dependent fit
$W(\rho)=S_0\,[1+a\rho^{b}/(1-\rho)]$ with $\rho=\lambda/\mu$, whose two parameters are fitted to
the stable training rates.

\section{Security--Performance Trade-off}\label{sec:tradeoff}
\subsection{What a Session Exposes}
In P1 every object has its own shared secret, and an attacker who obtains one learns one object.
In N1 the unit of compromise is the session root: whoever reads a root from process memory, a
crash dump, a swap file or a log can derive the data keys of every object it protected, at most
$B_{\max}$ objects written within $T_{\max}$ seconds. A cache shared between tenants would extend
that exposure across tenants, so roots must be scoped to one recipient key, as ours are. This
exposure is distinct from, and much smaller than, compromise of the recipient's long-term
decapsulation key, which exposes all objects in every mode. The theoretical $1/B_{\max}$
operations per object holds only when sessions fill before the time limit, so we report what was
observed.

\QaKemRatioLow$\times$ as often as a fixed bound of 100 at \QaRateLow{} requests/s with no
measurable change in tail latency; we did not show that it is better than a smaller fixed bound.

\subsection{Decision Rule}
The measurements support a conservative rule. Per-object ML-KEM is the default. Amortization is
enabled only for a workload in which profiling shows the client CPU to be the bottleneck, and
then with the smallest bound that achieves the gain: in our data $B_{\max}=10$ already removes
most of the CPU cost, so a larger bound buys exposure without benefit. $T_{\max}$ should be set
from the tolerated exposure of an idle client, since it is the limit that binds under light load.
The same reasoning applies to the choice between ML-KEM and a hybrid: where the client is not the
bottleneck the hybrid costs only \RevMetaXwingOverMLKEM{} bytes per object, and where it is, the
cost is the throughput difference reported in Section~\ref{sec:hybrid}.

\section{Robustness and Validity}\label{sec:validity}
\subsection{Run-to-Run Variation}
Fig.~\ref{fig:tost} shows every paired ratio of the primary family. Six cells are tight: the
coefficient of variation of throughput across runs is at most \RevCvQuietMax\,\%. The two
64\,KiB PUT cells vary by \RevCvNoisyLo--\RevCvNoisyHi\,\% per mode. That variation originates at
the server (Section~\ref{sec:bottleneck}) and affects all modes alike, which is why it widens
intervals without shifting ratios.

\subsection{Stalls}
The pre-registered rule flags \RevStalls{} of \RevRuns{} x86 runs and \ArmStalls{} of \ArmRuns{}
ARM runs, all of them PUTs of at most 64\,KiB. Excluding them leaves the 8 x86 verdicts
unchanged and turns one ARM verdict, the knee cell, from equivalent to inconclusive
(Section~\ref{sec:primary}).

\subsection{Order and Time Effects}
Modes are shuffled within each repetition. As a check, for each primary cell we regress log
throughput on the mode, repetition fixed effects, elapsed time in the batch, position in the
block and whether the previous run was a PUT. The adjusted P1/B2 ratio differs from the paired
ratio by at most \RevOrderShiftMax\,\% in any cell on either architecture.

\subsection{Second Architecture}
The ARM replication reproduces the pattern: equivalence at 1\,MiB and above, a deficit of
\RevHotDeficit\,\% (x86) and \ArmHotDeficit\,\% (ARM) in the client-bound cell, and noise in small PUT. Because that testbed also has another server
instance, it tests the robustness of the ratios and not ARM against x86 in absolute terms.

\subsection{Threats to Validity}
\textbf{Internal.} Stage timers above one worker include interpreter-lock waiting, so
key-establishment time is reported at one worker only. The exploratory campaign's pause failure
(Section~\ref{sec:method}) added noise to small PUT cells; its results for those cells come from
batch D. The 1\,MiB one-worker slowdown of the hybrids is unexplained. The profiling attribution
names a subsystem, not a function. The two inconclusive primary cells were under-powered.

\textbf{External.} These are the limits of what the data supports. The client is Python with
liboqs through a binding: absolute key-establishment times include call overhead, and a native or
hardware-accelerated client could show a different ratio between modes, most likely where the
client CPU is the bottleneck. MinIO ran as a single node without erasure coding or replication;
a distributed deployment has a different write path and may have a different ceiling and knee.
Both hosts sat in one placement group with a sub-millisecond round trip; a wide-area client would
be dominated by the network. All runs used AWS, in two regions, with one server instance type.
liboqs is intended for prototyping, not production.

\textbf{Construct.} Throughput equivalence within $\pm$5\,\% is an engineering criterion, not a
statement that two modes are identical. The exploratory verdict counts are not corrected for
multiplicity. Runs last 20\,s; slower effects such as compaction or long-term memory growth are
not observed.

\section{Discussion}\label{sec:discussion}
\textbf{Migration planning.} In the evaluated configuration, per-object ML-KEM-768 changes
capacity only where the client CPU is already the bottleneck, and there by
\RevHotDeficit--\ArmHotDeficit\,\%. An operator
of a comparable deployment can plan the migration around compatibility, key management and
metadata growth; the throughput question should be re-measured for workloads of many small reads
from few clients, and for any client stack other than ours.

\textbf{Where the cost lies.} The measurable costs are \RevMetaExtraMLKEM{} bytes of metadata per
object and, for hybrids, a client-CPU increment that shows only under client saturation.
RSA-4096 is the poor choice: its private-key operation makes small-object reads CPU-bound at
\RevRsaGetLo--\RevRsaGetHi{} of ML-KEM's throughput.

\textbf{Capacity planning.} The open-loop results matter more than the cryptographic choice. In
this store response time degrades at \RevQSmallRhoLastStable--\RevQMidRhoFirstUnstable{} of
peak throughput, and capacity
measured in a closed loop overstates what an open arrival stream can sustain. Provisioning should
target the knee, measured under open-loop load.

\section{Conclusion and Future Work}\label{sec:conclusion}
We evaluated per-object post-quantum key establishment on one client stack (Python
\PythonVersion, liboqs \LiboqsVersion), a single-node MinIO server and AWS instances in two
regions, with x86 and ARM clients. Under these conditions ML-KEM-768 takes
\RevKeMLKEMPut--\ArmKeMLKEMGet\,ms per object across the two clients, is equivalent to X25519 within $\pm$5\,\% in
\RevPrimaryEq{} of 8 pre-registered cells on each architecture and non-equivalent in none, and
is \RevHotDeficit--\ArmHotDeficit\,\% slower where the client CPU is the bottleneck. X-Wing is
affordable except in that client-bound regime, where it costs
\RevXwingHotDeficit--\ArmXwingHotDeficit\,\%. The costs that remain are \RevMetaExtraMLKEM{} bytes of metadata per object and a small
client-CPU increment; bounded sessions are justified only where that increment is a measured
bottleneck. These results should not be extended to distributed object stores, other S3
implementations, native clients or wide-area deployments without new measurements.

Future work follows from these limits: a native client to separate interpreter overhead from
cryptographic cost; distributed MinIO and a second S3 implementation; more repetitions of the
small-object write cells; a queueing model that represents capacity fluctuation; and
post-quantum signatures for object integrity.
