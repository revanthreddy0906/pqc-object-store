\begin{abstract}
Data at rest that is encrypted under classical public-key algorithms can be recorded now and
decrypted once a large quantum computer exists; public-key envelope encryption must therefore move to
ML-KEM, which places a key-encapsulation operation and its ciphertext on every object. To our knowledge its cost has been measured for primitives and for connection setup, but not on
a concurrent object-store data path. We measured it on an S3-compatible store with a Python client
on two processor architectures and a native Go reader, comparing ML-KEM with X25519 and two
hybrid modes in an exploratory campaign, a pre-registered confirmatory campaign with paired
equivalence tests, and pre-registered controls. With one unexplained exception in the native reader, ML-KEM lowered throughput only where
the client was at or near CPU saturation: there the Python client was \RevHotDeficit{} to
\ArmHotDeficit\,\% slower than with X25519. Two controls on the x86 client show that the
deficit there is produced by the library binding, which makes four foreign calls per decapsulation;
with one call, ML-KEM was equivalent to X25519 within 2\,\%. A native reader saturated on one
core was \AudNOneMlkemDeficit\,\% slower, so the size of the cost depends on the implementation. The cost that every implementation pays is storage: \RevMetaIntrinsic{} more bytes of
ciphertext per object than X25519. The results cover two clients, a single-node store
and one cloud provider.
\end{abstract}

\section{Introduction}
Cloud object stores keep data for years, and much of that data is encrypted under keys
established with RSA or elliptic-curve Diffie--Hellman. Shor's algorithm would allow a
sufficiently large quantum computer to recover those keys, so an adversary who records
ciphertext today can decrypt it once such a machine exists, a threat usually called
``harvest now, decrypt later''. For data at rest the exposure lasts as long as the data is
retained. In August 2024 NIST published FIPS~203, standardizing the module-lattice
key-encapsulation mechanism ML-KEM~\cite{fips203}.

With client-side envelope encryption, as implemented by the Amazon S3 Encryption Client and by
Azure Blob Storage client libraries~\cite{s3ec,azurecse}, every object is encrypted under its own
data key, and that key is protected for the recipient and stored with the object.

\textbf{When a public-key KEM per object is needed.} If writer and reader share a symmetric
key-encryption key, wrapping the data key with AES is already quantum-safe and no KEM is needed;
that is our baseline B1. A public-key mechanism is required when the writer must not be able to
decrypt, or does not share a secret with the reader: write-only producers such as log shippers,
backup agents and sensors that hold only a public key; objects encrypted to several recipients
or to an escrow key; and data handed across organizational boundaries. These deployments use RSA
or elliptic-curve key establishment today, and they are the ones that must migrate. For them,
ML-KEM places a key establishment and its 1{,}088-byte ciphertext on every PUT and every GET
rather than once per connection.

\textbf{What is known.} Primitive-level studies report the cost of key generation, encapsulation
and decapsulation and the sizes of keys and ciphertexts on several processor
families~\cite{liboqs,rodriguez2025,demir2025,lopez2025}. Studies of post-quantum TLS and KEMTLS
measure connection establishment under latency, loss and bandwidth limits
\cite{paquin2020,sikeridis2020,sosnowski2023,giron2023}. Storage studies measure the S3 interface
without cryptography~\cite{gadban2021} and client-side encryption without post-quantum key
establishment~\cite{henziger2019,ozeri2023}.

\textbf{What is not known.} None of these measures ML-KEM where an object store would use it: once
per object, on a data path whose throughput is set jointly by client CPU, network, metadata
handling and the storage server, with many clients at once. A back-of-envelope estimate already
says that tens of microseconds of KEM against milliseconds of storage round trip should be
invisible. What that estimate cannot say is whether it holds under concurrency, in which regime
it fails, by how much, and whether the cause is the KEM computation or the larger ciphertext it
carries through the data path (Section~\ref{sec:related}, Table~\ref{tab:gap}).

\textbf{Thesis.} In the configurations we measured, replacing X25519 by per-object ML-KEM lowered
throughput only where the client was at or near CPU saturation, with one unexplained exception
in the native reader. The size of the loss there depended on the client implementation: it
ranged from no measurable
loss (\AudBindReleasedRatio{} of X25519's throughput, the Python client calling liboqs through
one foreign call) through \RevHotDeficit--\ArmHotDeficit\,\% (the same client through the
standard binding) to \AudNOneMlkemDeficit\,\% (a native Go reader on one core). The cost that
every implementation pays is storage: a larger ciphertext with every object. The observations
that do not fit this picture are collected in Section~\ref{sec:anomalies}.

reader covers the GET path of three modes only. Section~\ref{sec:pending} lists the experiments
that remain and Section~\ref{sec:planned} the ones planned.

\section{Background}\label{sec:background}
\subsection{Key-Encapsulation Mechanisms and ML-KEM}
A key-encapsulation mechanism (KEM) consists of key generation, encapsulation, which takes the
recipient's public key and outputs a ciphertext and a shared secret, and decapsulation, which
recovers the secret with the private key. ML-KEM, derived from CRYSTALS-Kyber, relies on the
hardness of module learning with errors. ML-KEM-768 targets NIST security category~3 with a
1{,}184-byte encapsulation key, a 1{,}088-byte ciphertext and a 32-byte shared
secret~\cite{fips203}. Decapsulation uses \emph{implicit rejection}: a modified ciphertext yields
a pseudorandom secret instead of an error, so tampering is detected by the authenticated
encryption that follows.

\subsection{Hybrid KEMs}
A hybrid KEM combines a classical and a post-quantum component so that the result stays secure
while either remains unbroken. The combiner matters: X-Wing~\cite{barbosa2024,xwing} combines
X25519 with ML-KEM-768 as
$\mathrm{SHA3\mbox{-}256}(ss_M\|ss_X\|ct_X\|pk_X\|\mathit{label})$ and derives both private keys
from one 32-byte seed; its security proof depends on these concrete choices and does not carry
over to other ways of mixing two secrets.

\subsection{HPKE}
Hybrid Public Key Encryption (HPKE, RFC~9180)~\cite{rfc9180} is the standard construction for
encrypting to a public key: a KEM produces a shared secret, a key schedule derives an AEAD key
and base nonce from it and from application-supplied context, and messages are sealed under
sequence-numbered nonces. An IETF draft adds ML-KEM-768 and an X25519+ML-KEM-768 hybrid as HPKE
KEMs~\cite{hpkepq}. Per-object envelope encryption is an instance of HPKE's single-recipient
base mode.

\subsection{Envelope Encryption and Object Storage}
In envelope encryption a per-object data key encrypts the object, and key establishment protects
that key. We derive data keys with HKDF-SHA256~\cite{rfc5869} and encrypt with AES-256-GCM, whose
security requires that a nonce is never reused under one key~\cite{sp80038d}. The classical
alternatives are key transport with RSA-OAEP~\cite{rfc8017} and ephemeral-static X25519
\cite{rfc7748}. Object stores expose buckets and keys through HTTP operations, chiefly PUT and
GET of whole objects; the S3 interface is the de facto standard~\cite{gadban2021}. We use
MinIO~\cite{minio}, compiled from its final community release (\MinioRelease). Because that
community edition is no longer developed, our store-specific results (ceilings, knee) should be
read as those of one representative single-node S3 server, not as current product behaviour.

\subsection{Where Key Establishment Has Been Measured}
Existing measurements stop at two boundaries. At the primitive level, the Kyber design
paper~\cite{bos2018}, the standard~\cite{fips203}, library benchmarks~\cite{liboqs} and recent
comparative preprints~\cite{rodriguez2025,demir2025,lopez2025} give the cost and sizes of the
three KEM operations on several processor families; they establish that platform and
implementation matter, which is why we repeat our primary comparison on a second architecture
and test a second implementation, but they contain no storage, concurrency or end-to-end request
latency. At the transport level, studies of post-quantum TLS and KEMTLS
\cite{paquin2020,sikeridis2020,sosnowski2023,giron2023,schwabe2020} measure connection
establishment under latency, loss and bandwidth limits and decompose the handshake. They are the
closest systems precedents, but their amortization boundary differs: a handshake protects a
connection, whereas in client-side object encryption key establishment and its ciphertext recur
for each object.

\subsection{Per-Message Key Establishment in Messaging}
The closest analogue of a per-object KEM with bounded reuse is secure messaging, where
post-quantum KEMs have been added to session setup and to periodic rekeying
\CITE{Signal; The PQXDH Key Agreement Protocol; specification; 2023; VERIFY}
\CITE{Apple Security Engineering; iMessage with PQ3; technical report or blog; 2024; VERIFY}.
There the unit of amortization is a session or a ratchet epoch, and the question of how many
messages one KEM output may protect is the same one our session mode poses for objects
(Section~\ref{sec:tradeoff}). We are not aware of throughput measurements of these protocols
that would transfer to an object store. \TODO{Authors: read both sources and confirm this

\subsection{Storage and Client-Side Encryption}
Storage studies measure the S3 interface without cryptography, and client-side encryption
without post-quantum key establishment. Gadban and Kunkel~\cite{gadban2021} attribute losses on
the S3 path to layers of the client stack, a separation our harness applies to cryptographic
stages; Henziger and Carlsson~\cite{henziger2019} and Ozeri et al.~\cite{ozeri2023} concern
where client-side encryption sits and what it costs synchronization. Two 2026 preprints
approach post-quantum cloud storage from the design side: Prikutse et
al.~\cite{prikutse2026} combine AES-256-GCM, X25519+ML-KEM-768 and ML-DSA-65 and amortize
signatures over a batch of files, and Junaid~\cite{junaid2026} proposes a client-side hybrid
architecture with self-hosted key management. According to their abstracts, neither evaluates
concurrent S3 PUT/GET or compares with classical per-object key establishment; we have read only
the abstracts. Bounded key reuse is established practice in this setting: Amazon S3 Bucket Keys
derive per-object data keys from a time-limited bucket-level key and reduce key-service requests
by up to 99\,\%~\cite{s3bucketkeys}, and the AWS Encryption SDK caches data keys under age,
message and byte limits~\cite{esdkcache}. Our session mode applies that principle to ML-KEM
roots and quantifies the trade-off.

\subsection{Standard Constructions and KEM Combiners}
HPKE~\cite{rfc9180} and its post-quantum extension~\cite{hpkepq} specify how to encrypt to an
ML-KEM or hybrid public key but contain no measurements; the file-encryption tool age adopted
such recipients~\cite{age2025}. Our envelope predates our reading of that draft and is not
HPKE-conformant; Section~\ref{sec:hpke} maps one onto the other and states what transfers. For
hybrids, the security of the result depends on the combiner. X-Wing~\cite{barbosa2024,xwing}
comes with a proof for its concrete combiner, and the general theory of KEM combiners states the
conditions under which a combination stays secure if one component fails
\CITE{Giacon, Heuer, Poettering; KEM Combiners; PKC; 2018; VERIFY}
\CITE{Bindel, Brendel, Fischlin, Goncalves, Stebila; Hybrid Key Encapsulation Mechanisms and Authenticated Key Exchange; PQCrypto; 2019; VERIFY}.
Our mode P2 concatenates two shared secrets into HKDF and has not been checked against those
conditions, which is why it carries no security claim and serves only as a performance
reference (Table~\ref{tab:claims}).

\subsection{Performance Variability and Benchmarking Statistics}
Three strands of method inform our design. Cloud instances show run-to-run and time-dependent
performance variation large enough to change conclusions drawn from single runs
\CITE{Leitner, Cito; Patterns in the Chaos: A Study of Performance Variation and Predictability in Public IaaS Clouds; ACM TOIT; 2016; VERIFY}
\CITE{Uta et al.; Is Big Data Performance Reproducible in Modern Cloud Networks?; NSDI; 2020; VERIFY}
\CITE{Maricq et al.; Taming Performance Variability; OSDI; 2018; VERIFY},
which is why our experimental unit is the independently restarted run, compared in randomized
blocks and never across sessions. Reporting rules for performance measurements
\cite{hoefler2015} \CITE{Kalibera, Jones; Rigorous Benchmarking in Reasonable Time; ISMM; 2013; VERIFY}
ask for intervals over independent repetitions and a full description of the setup. Schroeder et

\section{System and Threat Model}\label{sec:design}
\subsection{Threat Model}
The network and the object store are honest-but-curious for confidentiality and potentially
malicious for integrity: an adversary may read, replace, delete, reorder or replay stored
ciphertexts and manifests. The adversary does not hold the recipient's decapsulation key and may
in the future operate a quantum computer. Availability, traffic analysis, deletion of whole
objects, compromised endpoints and side channels in the client are out of scope.

\textbf{Writers are not authenticated.} The envelope encrypts to a public key and carries no
signature, as HPKE base mode does not either. Integrity therefore means that an object written
by an honest writer cannot be modified, reordered, truncated, extended or spliced without
detection. It does not mean that an object is authentic: anyone who knows the recipient's public
key, including the store, can create a new object under any identity, and it will decrypt
without error. Sender authentication is out of scope.

\textbf{Rollback is not prevented.} Replay is detected only where it crosses an identity: a
manifest or chunk moved to another object or another version fails authentication, because the
object identity and version are bound into the key and into every chunk. Serving an
\emph{older, complete and valid version} of the same object is a different matter. A store that
withholds or deletes the newest manifest makes the reader accept the previous version, and
nothing in the design detects that. Freshness would need state outside the store, such as a
signed version counter or a transparency log; it is out of scope.

\textbf{Key commitment.} AES-GCM is not key-committing: a ciphertext can be constructed that
decrypts validly under more than one key
\CITE{Dodis, Grubbs, Ristenpart, Woodage; Fast Message Franking: From Invisible Salamanders to Encryptment; CRYPTO; 2018; VERIFY}
\CITE{Len, Grubbs, Ristenpart; Partitioning Oracle Attacks; USENIX Security; 2021; VERIFY}.
We accept this for the single-recipient setting studied here, on the following argument. Since
writers are not authenticated, a malicious writer can already store any plaintext it likes
under a key the recipient will derive; a ciphertext that also decrypts under a second key gives
it no further capability against one recipient. That argument is not a proof and we make no
formal claim (Table~\ref{tab:claims}). It does not extend to several recipients, where one
ciphertext could decrypt to different plaintexts for different recipients, or to
password-derived keys: a multi-recipient design (Section~\ref{sec:planned}, E2) must use a
key-committing construction
\CITE{Albertini et al.; How to Abuse and Fix Authenticated Encryption Without Key Commitment; USENIX Security; 2022; VERIFY}.

\subsection{Key-Establishment Modes}
Table~\ref{tab:modes} lists the modes. All encrypting modes share the HKDF and chunked AES-GCM
path. They differ in the key-establishment computation \emph{and} in the size of the manifest
that carries its ciphertext (622 to 2{,}085 bytes), which changes parsing, hashing and bytes
transferred. A difference between two modes is therefore the cost of key establishment together
with the handling of its ciphertext; Section~\ref{sec:mechanism} separates the two as far as
the data allows. B0 stores plaintext through the same
framing; B1 derives keys from a pre-shared 32-byte key and is the symmetric-only floor; R1
transports a random secret with RSA-OAEP-4096; B2 uses ephemeral-static X25519; P1 uses
ML-KEM-768. Two hybrids combine X25519 with ML-KEM-768. \emph{P3 is X-Wing} as specified in
\cite{xwing}: we implement its key derivation from a 32-byte seed, its SHA3-256 combiner and its
ciphertext layout, and verify key generation, encapsulation and decapsulation against the
draft's published test vectors. \emph{P2 is a study-specific concatenation hybrid}: it stores the
ML-KEM ciphertext followed by the X25519 ephemeral key and feeds both 32-byte secrets,
concatenated, to HKDF together with the object context. P2 predates our X-Wing implementation; we
keep it as a performance reference and make no security claim for its combiner. N1 amortizes one
ML-KEM encapsulation over a bounded session (Section~\ref{sec:n1design}). A reader must name the
mode it expects, so a planted plaintext object cannot downgrade an encrypted one.

\subsection{Per-Object Envelope and Commit Protocol}
Algorithm~\ref{alg:putget} shows PUT and GET for mode P1. An object is identified by
$I=(\mathit{tenant},\mathit{bucket},\mathit{key},\mathit{version})$, where versions are
time-ordered UUIDv7 values. The context $\mathit{ctx}$ is canonical JSON of $I$, the mode, the
algorithm names, chunk size and count, plaintext size, recipient key identifier and the SHA-256
hash of the key-establishment ciphertext $C$; it is bound into the data key and into every chunk.
Objects are split into 4\,MiB chunks, and chunk $j$ is encrypted with nonce
$p\|\mathrm{be}_{64}(j)$ under a random 32-bit prefix $p$ and associated data
$\mathit{ctx}\|j\|\ell_j\|\mathit{final}_j$, so deletion, reordering, truncation, extension and
cross-object splicing of chunks fail authentication. This is the counter-and-final-flag pattern
of the STREAM construction~\cite{hoang2015}, with the flag carried in the associated data
instead of the nonce; we do not claim STREAM's proof for our variant. Each version is stored under
\texttt{key.pqcs/version/} as a ciphertext stream \texttt{data.enc} and a manifest
\texttt{manifest.json} holding $\mathit{ctx}$, $C$, the salt and the prefix. The manifest is
written last and serves as the commit record: readers only consider versions whose manifest
exists, so an interrupted upload is never visible. One logical PUT is therefore two S3 writes
(the data, in parts above 8\,MiB, then the manifest), and one GET of a known version is two S3
reads (the manifest, then the data). Finding the newest version needs an additional LIST, which
the benchmark avoids by reading versions it knows; a client that always asks for ``the latest''
would pay it.

\begin{algorithm}[t]
\caption{Per-object PUT and GET (mode P1)}
\label{alg:putget}
\footnotesize
\begin{algorithmic}[1]
\Procedure{Put}{$\mathit{key}, M, ek$}
\State $v \gets \textsc{UUIDv7}()$; \ $I \gets (\mathit{tenant},\mathit{bucket},\mathit{key},v)$
\State $(C,S) \gets \mathrm{ML\mbox{-}KEM.Encaps}(ek)$
\State $\mathit{salt} \xleftarrow{\$} \{0,1\}^{256}$; \ $p \xleftarrow{\$} \{0,1\}^{32}$
\State $\mathit{ctx} \gets \textsc{Canon}(I,\text{mode},n,|M|,\mathrm{id}(ek),\mathrm{H}(C),\dots)$
\State $K \gets \mathrm{HKDF}(S,\mathit{salt},\text{``pqc-s3-object-v2''}\|0\|\mathit{ctx})$
\For{$j \gets 0$ \textbf{to} $n-1$} \Comment{4\,MiB chunks}
\State $c_j \gets \mathrm{AES\mbox{-}GCM}_K(p\|\mathrm{be}_{64}(j), M_j, \mathit{ctx}\|j\|\ell_j\|\mathit{final}_j)$
\EndFor
\State upload $c_0\|\dots\|c_{n-1}$ in 8\,MiB parts to \texttt{key.pqcs/$v$/data.enc}
\State commit: write $(\mathit{ctx},C,\mathit{salt},p)$ to \texttt{key.pqcs/$v$/manifest.json}
\EndProcedure
\Procedure{Get}{$\mathit{key}, dk, \text{mode}$}
\State $v \gets$ newest version with a manifest; read and parse it
\State \textbf{reject} unless identity, mode, key id and $\mathrm{H}(C)$ all match
\State $S \gets \mathrm{ML\mbox{-}KEM.Decaps}(dk,C)$; \ $K \gets \mathrm{HKDF}(S,\mathit{salt},\dots)$
\For{each chunk $c_j$ of \texttt{data.enc}}
\State $M_j \gets \mathrm{AES\mbox{-}GCM}^{-1}_K(\dots)$; \ \textbf{reject} on failure
\EndFor
\State \textbf{reject} unless exactly $n$ chunks were read and the last is final
\EndProcedure
\end{algorithmic}
\end{algorithm}

\subsection{Bounded Sessions (Mode N1)}\label{sec:n1design}
In N1 one encapsulation yields a root $S_r$, and object $i$ of the session uses
\[K_i=\mathrm{HKDF}(S_r,\mathit{salt}_i,\text{``pqc-s3-session-v1''}\|0\|\mathit{ctx}_i),\]
with the session identifier, the object's sequence number and the bound authenticated in
$\mathit{ctx}_i$. Every object still stores the session's ML-KEM ciphertext, so it can be
decrypted alone. A root protects at most $B_{\max}$ objects and lives at most $T_{\max}$ seconds,
whichever is reached first. In a queue-aware variant the object bound of each new session is
\[B_t=\mathrm{clip}\bigl(B_{\min},B_{\max},\mathrm{round}(B_{\min}+(B_{\max}-B_{\min})\hat\rho)\bigr),\]
where $\hat\rho$ is a moving average ($\alpha=0.2$) of the fraction of a client process's worker
threads with a request in flight. Receivers cache decapsulated roots under their own caps and
reject objects whose authenticated sequence number exceeds them.

\subsection{Relation to HPKE}\label{sec:hpke}
Our envelope has the structure of HPKE base mode~\cite{rfc9180}: one KEM encapsulation, a key
derivation bound to application context, and AEAD encryption of a sequence of records. It
differs in three ways. (1)~The data key is derived with a single HKDF-SHA256 call whose
\emph{info} is the object context, where HPKE uses a labelled extract-and-expand key schedule
that also outputs a base nonce. (2)~Chunk nonces are a random prefix followed by a counter, where
HPKE computes base nonce XOR sequence number. (3)~The chunk index, length and final-chunk flag
are authenticated in the associated data; HPKE leaves truncation protection to the application.
Mode P1 uses a KEM that~\cite{hpkepq} defines for HPKE (ML-KEM-768). That draft also defines an
X25519+ML-KEM-768 hybrid under the KEM identifier that the X-Wing draft~\cite{xwing} requests,
so P3 corresponds to it; we did not test interoperability. A deployed example of this approach is
the file-encryption tool age, whose version 1.3.0 added HPKE-based hybrid ML-KEM-768 recipients
\cite{age2025}. It shows that a per-file post-quantum KEM is already practice; we found no
performance study of it under concurrent load. We did not
implement or benchmark HPKE. Since an HPKE-based envelope would perform the same KEM operation
once per object, a key schedule of a few hash calls and the same AEAD, we expect the per-object
costs reported here to transfer, but that expectation is untested, and a new design should use
HPKE and not this format.

\subsection{Cryptographic Core}
ML-KEM-768 comes from liboqs~\LiboqsVersion{} through liboqs-python~\LiboqsPyVersion{}
\cite{liboqs,liboqspython}. We build liboqs from a pinned release with only the ML-KEM parameter
sets enabled and load it from an explicit installation path, so the benchmark cannot silently pick up a different library; a start-up check verifies the library version and that ML-KEM-768 is enabled, and every call checks key and ciphertext sizes.
RSA-OAEP-4096 (SHA-256), X25519, HKDF and AES-256-GCM come from
pyca/cryptography~\CryptographyVersion{}~\cite{pyca}. A registry maps each mode to its
key-establishment and recovery functions, and the envelope module turns the result into a
streaming chunk encryptor or decryptor, so the storage code never holds a whole object. Before
any timed operation every worker process runs a warm-up that loads the libraries, performs a key generation, encapsulation, decapsulation, derivation and encryption round trip, and one full round trip in the mode under test, so that one-off costs never enter a timer.
An interoperability test checks ML-KEM in both directions against an independent implementation
(OpenSSL through pyca), and the manifest parser rejects unknown or missing fields, wrong types, inconsistent sizes and a key-establishment ciphertext that does not match its hash.

X-Wing uses the same liboqs build for its ML-KEM component, through the library's derandomized
key-generation and encapsulation functions, and the same X25519 as mode B2, so a difference
between P3 and P1 or B2 reflects the construction and not a different library. The expanded
decapsulation key is cached per process, which the draft permits; P1 likewise holds its expanded
key.

\subsection{Storage Layer}
The storage layer implements the commit protocol of Algorithm~\ref{alg:putget} on the MinIO
Python SDK~\MinioPyVersion. Ciphertext records are passed to the SDK through a file-like adapter
over the encryptor's output, so an object is uploaded in 8\,MiB parts while it is being encrypted;
on GET the stream is decrypted chunk by chunk into a sink. For benchmarking, the HTTP client uses a connection pool sized to the worker threads and performs no automatic retries, so failures are counted rather
than hidden inside latency. Auxiliary functions list committed versions, verify a commit by reading
it back, delete versions and collect uncommitted data left behind by interrupted uploads.

\subsection{Measurement Harness}
A \emph{run} executes one configuration (mode, operation, object size, concurrency and loop type)
with freshly started worker processes; it is the unit of replication. Concurrency $N$ is realized
as exactly $N$ worker threads spread over $\min(N,16)$ processes, one per vCPU. Each process warms
up, reports readiness, and all of them start at a common wall-clock instant, so that no worker
measures while others are still starting. Each run has a 5\,s warm-up phase and a 20\,s measured
phase; Python's garbage collector is run before and disabled during the timed window, so its
pauses cannot land inside a stage timer. In closed-loop runs each thread issues requests back to
back. In open-loop runs each process draws Poisson arrivals at its share of the target rate, a
request waits in a queue for a free thread, and the wait is recorded separately; a request that
cannot start before the end of the run is recorded as a failure, never dropped. GET runs read a
set of pre-written fixture objects that are created before and deleted after the run, and every
object written by a PUT run is deleted afterwards, outside the timed window.

Every request, including warm-up requests and failures, produces one record with
\texttt{perf\_counter} timers for the five stages of Algorithm~\ref{alg:putget} (key
establishment, key derivation, AES-GCM, manifest handling and storage), its total latency, the
thread CPU time it consumed, bytes on the wire and metadata size, plus identifiers that tie it to
its run, repetition, code commit and configuration. A client sampler records the CPU time and
resident memory of the worker processes and the host's CPU and network counters once per second;
a server sampler reads the same information from MinIO's Prometheus metrics endpoint and, in
the confirmatory campaign, dirty and write-back memory, disk write rate and latency, and I/O wait
from a node-exporter endpoint on the server host.

\subsection{Validation}
A validator checks every data set before analysis and refuses it if any check fails: checksums of
all files; a complete schema with correct types for every record; that no request's stage times
exceed its total; that per run the 99th percentile of unaccounted time stays below 2\,\% of the
request time and below 1\,\% in aggregate; and that no N1 session exceeds its bound. The
\TestCount{} automated tests cover the cryptographic core, the commit protocol, tampering (bit flips; deleted, reordered, duplicated, truncated or extended chunks; swapped, replayed or relabelled manifests; mode downgrade), that manifests contain no secret material and private-key files are protected, session bounds under concurrent stress, and
end-to-end runs against a live MinIO.

\subsection{Testbed Automation}
A single script provisions and operates the cloud testbed: it creates both instances in one
cluster placement group with a firewall that admits SSH only from the operator's address, copies
the committed code, builds MinIO from source into a Docker image, formats the server's local NVMe
disk at boot, runs network (iperf3, ping) and disk (fio) baselines, starts experiments in a
detached session, fetches results and stops or deletes all resources. Before launch, a planner
estimates the run time and cost of each experiment configuration. To bound cost, both instances
stop themselves when idle, and the client stops itself shortly after an experiment completes.

\subsection{Native Reader}
For the replication of Section~\ref{sec:native} we wrote a second, deliberately small client in
Go (\AudNGo): the GET path of modes B2, P1 and P3, with ML-KEM-768, X25519, HKDF, SHA-3 and
AES-GCM from Go's standard library and the MinIO Go SDK. A test opens objects written by the
Python client in all three modes and several sizes and rejects modified ciphertexts and a wrong
expected mode, so the two clients agree on the object format. Because Go's ML-KEM takes keys
as seeds, the recipient keys for this client are generated from seeds on the Python side. Its
benchmark runs goroutines in one process and reports throughput, process CPU and latency; it
has no stage timers.

\subsection{Analysis Pipeline}
A summarizer streams the compressed request records of each experiment once and writes one row
per run. A statistics stage computes intervals, paired equivalence tests, bottleneck labels and
the queueing models. A final stage generates every figure, table and number in this paper as
\LaTeX{} macros, so no result is typed by hand.

\subsection{Workload}
PUT and GET are measured separately, mostly in a closed loop. Each run has a 5\,s warm-up and a
20\,s measured phase. The exploratory campaign measures concurrency 1--500 at 64\,KiB and
1\,MiB (16\,MiB up to 128 workers) and object size 1\,KiB--500\,MiB at one worker. The
confirmatory campaign measures the primary cells defined below; a hybrid matrix of 1\,KiB to
128\,MiB at 1 and 128 workers; sessions at $B_{\max}\in\{1,10,100,1000\}$ and
$T_{\max}\in\{1,10,60\}$\,s; and, for the queueing analysis reported in the supplementary
material, closed-loop throughput at 1--256 workers and Poisson arrivals at 12 rates from
1{,}500 to 5{,}600 requests/s served by 256 threads, for 1\,KiB and 64\,KiB PUT. The
pre-registered queueing protocol (alternate rates as training and held-out points, scored by
error on the stable held-out rates) is stated in full there.

\subsection{Metrics}
\begin{itemize}
\item \emph{Per-object key-establishment time}: the time a request spends in encapsulation, RSA
unwrapping, Diffie--Hellman or decapsulation, from the stage timers. It is sometimes loosely
called ``handshake overhead''; we avoid that name because no multi-message protocol is
involved.
\item \emph{Throughput}: successful requests, or MiB, per second of the measured window.
\item \emph{CPU}: CPU of the client's benchmark processes and of MinIO during the measured
window, and client thread CPU time per request.
\item \emph{Memory}: peak resident memory and its growth over the run.
\item \emph{Response time} (open loop): queue wait plus service time per request.
\item \emph{Metadata}: bytes of the manifest stored with each object.
\end{itemize}
Above one worker, stage timers include time spent waiting for the Python interpreter lock, so
key-establishment time and stage shares are reported at one worker only.

\subsection{Experimental Unit and Replication}
A run starts fresh worker processes and is the experimental unit. The millions of requests inside
a run sharpen that run's own estimate; they are not independent replicates, and no interval in
this paper is computed over requests. Runs are organized in randomized complete blocks: one
repetition contains every mode of a cell once, in shuffled order, and modes are compared only
within a repetition.

Between runs the harness waits until the server host's dirty plus write-back memory is below
32\,MiB and its disk write rate below 5\,MiB/s for two consecutive seconds, at most 40\,s. In the
exploratory experiments \lab{Expl-Sweep}, \lab{Expl-Size} and \lab{Expl-OpenLoop} this pause had silently fallen back to 5\,s, which slowed some PUT runs
that followed another PUT run by \StallSlowMin--\StallSlowMax\,\%; \lab{Expl-SmallPUT} repeated the affected
cells with a fixed 40\,s pause. In the confirmatory campaign the measured pause had a median of
\RevSettleMedian\,s.

\subsection{Equivalence Testing}\label{sec:tost}
For a cell and two modes $a$ and $b$, repetition $i$ gives the paired log ratio
$d_i=\log(x_{a,i}/x_{b,i})$ of throughput. We test equivalence with two one-sided tests
(TOST)~\cite{schuirmann1987,dixon2018} against the bounds $[\log 0.95,\log 1.05]$:
\[H_0^{-}:\ \mathrm{E}[d]\le\log 0.95,\qquad H_0^{+}:\ \mathrm{E}[d]\ge\log 1.05,\]
each with a one-sided paired $t$-test at $\alpha=0.05$. The modes are declared \emph{equivalent}
only if both are rejected, which is the same as the 90\,\% confidence interval of the ratio lying
inside $[0.95,1.05]$; the TOST $p$-value is the larger of the two. We also show the 95\,\%
interval for estimation. A cell whose 90\,\% interval lies wholly outside the bounds is
\emph{non-equivalent}; anything else is \emph{inconclusive}, which is not evidence of ``no
difference''.

\textbf{Margin.} Five percent is our smallest effect of interest and was fixed in advance, as the
margin the exploratory campaign had already used. Its practical meaning is a provisioning one: a
5\,\% loss of capacity raises utilization by the same factor, so a deployment planned at or
below \RevMarginUtil{} of peak throughput stays under the stability boundary we measure for
this store (supplementary material) and needs no additional capacity. That argument uses a result of this
study and was made after the fact; an operator with a tighter target needs a tighter margin,
which is why we report sensitivity at $\pm$2\,\% and $\pm$10\,\%
\cite{lakens2017}.

\textbf{Primary family and multiplicity.} The confirmatory hypothesis is the ratio P1/B2 in eight
closed-loop cells chosen before the campaign: 64\,KiB GET at 128 and 500 workers; 64\,KiB PUT at
32 workers (the knee of the throughput curve) and 128; 1\,MiB PUT and GET at 32; and 16\,MiB PUT
and GET at 32. The eight $p$-values are adjusted with Holm's procedure~\cite{holm1979}, which
controls the family-wise error rate. \emph{A limitation of this family, recognized after the
campaign:} only one cell, 64\,KiB GET at 500 workers, has a saturated client. The 64\,KiB PUT
cells are limited by the server and the four cells at 1\,MiB and above by the network or the
server; at 64\,KiB GET with 128 workers the client is the busiest resource but still has spare
CPU, which a costlier mode simply uses (Section~\ref{sec:cpumethod}). In seven of eight cells,
therefore, no key-establishment mode could have changed throughput, and equivalence there
confirms where the bottleneck is and little about ML-KEM. Throughput is also
an insensitive endpoint in those cells; we therefore add client CPU per request as an
exploratory second endpoint (Table~\ref{tab:cpuprimary}). The same family measured on the ARM client is a replication
and is adjusted in the same way. All other comparisons (P3 and P2 against P1 and B2, R1 against
P1, and every cell outside the family) are exploratory and reported with unadjusted intervals.

\textbf{Power.} From the paired log-ratio standard deviations of the exploratory campaign, a
normal-approximation calculation at $\alpha=0.05/8$ and power 0.8 required at most 7 repetitions
in every primary cell except the knee, which required about 19. We therefore ran 10 repetitions
per cell and 20 at the knee, with no optional stopping.

\textbf{Distributional assumption.} The $t$-tests assume approximately normal mean log ratios
from 10 or 20 pairs. As a check we recompute each primary verdict from a percentile-bootstrap
90\,\% interval of the mean log ratio (20{,}000 resamples).

\textbf{Stall rule.} Fixed in advance and blind to the mode: a closed-loop run is a \emph{stall}
if its server CPU is below 0.8 times and its throughput below 0.9 times the median of its own
cell. The primary analysis uses all runs; excluding stalls is a sensitivity analysis.

\subsection{CPU Accounting as a Method}\label{sec:cpumethod}
Throughput is cores in use divided by CPU per request. If the client CPU is exhausted, two modes
use the same number of cores, and the throughput ratio of mode $a$ to mode $b$ is the inverse
ratio of their client CPU per request,
\[\frac{X_a}{X_b}=\frac{c_b}{c_a}.\]
This is an accounting identity, not an empirical finding and not a model with free parameters:
evaluated on the runs it describes, its error measures only how equal the core counts of the two
modes are. We use it as a method, in two ways. It localizes a throughput difference: if the
identity holds, the difference has no source other than client CPU. And it gives an operator a
procedure: measure CPU per request for the current and the candidate mode on the real client,
check whether the client is saturated, and read off the expected change.

\textbf{Saturation criterion.} For the native reader the criterion was fixed in advance: a cell
is client-saturated if process CPU is at least 0.95 of the cores made available, in every mode.
For the Python client no criterion was pre-registered, and we do not claim a sharp one. In the
64\,KiB GET cells the post-quantum modes use nearly the same number of cores as X25519 at 500
workers and visibly more at 128 workers (Table~\ref{tab:model}); RSA-4096 uses more cores than
X25519 in both. We therefore write ``at or near saturation'' and describe the regime by what
was observed (next paragraph), not by a threshold.

\textbf{What counts as a throughput deficit.} To say where ML-KEM lowered throughput we apply
one rule to every closed-loop cell in which the Python client ran both ML-KEM and X25519: a
\emph{deficit} if the 90\,\% interval of the paired throughput ratio lies below 0.98, an
\emph{advantage} if it lies above 1.02. This is the rule pre-registered for the native reader;
applying it to the other experiments was decided afterwards and is exploratory
(Section~\ref{sec:deviations}).

\textbf{Status as a prediction.} The identity becomes a prediction only when applied to data it
was not computed from. We did that once, with a ratio fixed before two follow-up experiments;
it missed (Section~\ref{sec:mechanism}).

\subsection{Deviations from the Pre-Registration}\label{sec:deviations}
(1) The first attempt at \lab{Primary-x86} (batch E) was cut off after 134 of 300 runs when an account-level spending
guard stopped both instances. Its data was never downloaded or analysed; the batch was restarted
from its first run with the same configuration and seed. (2) \lab{Profiling} was run twice,
once under system-call tracing and once under CPU sampling, because the first CPU profiles were
unusable. (3) The stall rule is applied to closed-loop runs only, since open-loop throughput is
fixed by the offered rate. (4) The pre-registration of \lab{Control-Binding} was pushed five minutes after
\lab{Control-Manifest} had started; it concerns \lab{Control-Binding} and a prediction for
\lab{Control-Manifest}, none of whose data had been downloaded. (5) The disk baseline of the
testbed of the follow-up experiments did not complete; its network baseline did.

\textbf{Not pre-specified.} The pre-registration fixed the primary family, its test and the
training and held-out split. It did not fix the following, which were chosen during analysis and
are exploratory: applying Holm's correction to the ARM family as well; client CPU per request as a
second endpoint; the CPU accounting of Section~\ref{sec:cpumethod}, the saturation criterion for
the Python client, the sweep of all cells with the deficit rule and the stage comparison of
Section~\ref{sec:mechanism};
the single-thread timing of the native reader's key recovery;
the bootstrap check; the definition of the knee as twice the light-load response time; the
functional form of the load-dependent model; the order-and-time regression of
Section~\ref{sec:validity}; and the layout of the session and hybrid tables.

alone costs \AudPadCost\,\% of throughput (ratio \AudPadRatio, 90\,\% CI \AudPadCI). ML-KEM

\subsection{Metadata at Scale (RQ1)}\label{sec:metadata}
The lasting cost of post-quantum key establishment is storage. Table~\ref{tab:meta} converts the
per-object manifest into fleet totals. An ML-KEM manifest is \RevMetaMLKEM\,bytes,
\RevMetaExtraMLKEM{} more than X25519; X-Wing adds another \RevMetaXwingOverMLKEM. Two parts of
that difference must be kept apart. The \emph{intrinsic} cost of ML-KEM is its ciphertext,
\RevMetaIntrinsic{} bytes more than an X25519 public key. The remaining
\RevMetaEncodingOverhead{} bytes are our encoding: the manifest is JSON and carries the
ciphertext in base64 (\RevMetaBaseSixtyFour{} characters), plus \RevMetaNameBytes{} bytes for a
longer algorithm name. For one billion objects the difference is \RevMetaBillionTB\,TB
(\RevMetaBillionTiB\,TiB) in this encoding and \RevMetaIntrinsicBillionTB\,TB with a binary
one.
Relative to the payload it is negligible from 1\,MiB upward and larger than the payload itself at
1\,KiB. These are logical bytes: replication or erasure coding multiplies them, and because the
manifest is a separate S3 object in our design, it also doubles the number of stored objects and
write requests, which matters under per-request billing and for inventory scans. Carrying the
manifest in the object's own metadata, as the Amazon S3 Encryption Client does by
default~\cite{s3ec}, would avoid the second object. Amazon S3 limits user-defined metadata to
2\,KB per object~\cite{s3metadata}: our JSON manifests for ML-KEM and both hybrids
(\RevMetaMLKEM--\RevMetaStudyHybrid\,bytes) are at or above that limit, whereas a binary
manifest (a 1{,}088-byte ciphertext and a few hundred bytes of context) would fit, provided the
store accepts binary metadata values or the client pays the base64 expansion once more in the
header. Our storage results therefore describe a two-object, JSON-manifest design, which we
chose so that an interrupted upload is never visible and a manifest can be read without the
data; they overstate both the bytes and the request count of a metadata-based design.

\subsection{Open Anomalies}\label{sec:anomalies}
Five observations are not explained by anything above. We list them together so that they are
not read past.

\textbf{(A1) A slower key derivation with ML-KEM.} At one worker the key-derivation stage is
+\RevGetStageKdfDelta\,\textmu s (x86) and +\ArmGetStageKdfDelta\,\textmu s (ARM) slower on GET
with ML-KEM than with X25519, although its inputs have the same length in both modes. The
padded-manifest control does not show it (+\AudKdfOverPadGet\,\textmu s for ML-KEM over the
padded control), so it is not an effect of manifest size. We have no explanation.

\textbf{(A2) A native deficit without saturation.} In \lab{Native-GET} with 16 cores and 128
workers ML-KEM is \AudNMidMlkemDeficit\,\% and X-Wing \AudNMidXwingDeficit\,\% slower than
X25519, in a cell that does not meet the pre-registered saturation criterion
(\AudNMidCores{} cores in use). Two cautions apply: the 16 virtual CPUs are 8 physical cores, and
the reader's CPU per request is two to three times higher with 16 cores than with one, which
suggests runtime overhead that makes ``cores in use'' a soft measure of saturation here. This
result is the one exception to the statement that ML-KEM lowered throughput only at or near
client saturation.

\textbf{(A3) X-Wing below X25519 in a Python cell we call unsaturated.} At 64\,KiB GET with 128
workers X-Wing is \RevXwingMidDeficit\,\% (x86) and \ArmXwingMidDeficit\,\% (ARM) slower than
X25519 (Table~\ref{tab:secondary}), although by our criterion that cell is not saturated. The
client is the busiest resource there, so this may be near-saturation; we did not test it.

\textbf{(A4) ML-KEM faster than X25519 at one worker.} By the deficit rule, ML-KEM has an
advantage in \AudSweepAdvantages{} cells of the exploratory campaign, both PUT at one worker
(ratios \AudSweepAdvantageLo{} and \AudSweepAdvantageHi, five runs each). Key establishment is
far too small a share of those requests to produce a difference of that size, and the
corresponding cells of \lab{Hybrid-Matrix} do not show an advantage by the same rule. We have
no explanation; an allocator effect of the kind described next is a candidate that we did not
test.

\textbf{(A5) An allocator effect at 1\,MiB.} In \lab{Hybrid-Matrix}, at 1\,MiB PUT with one worker X-Wing is
\RevMidPutXwingDeficit\,\% and P2 \RevMidPutStudyHybridDeficit\,\% slower than X25519 although key
establishment is \RevKeShareXwingMidPut\,\% of the request; the difference sits in the AES-GCM
stage timer, which all modes share. A diagnostic pair of experiments (\lab{Allocator}, \AudAllocRuns{} runs,
Table~\ref{tab:alloc}) points to the memory allocator. With default settings the AES-GCM stage
takes between \AudAllocDefaultLo{} and \AudAllocDefaultHi\,ms depending on the mode, a factor of
\AudAllocDefaultSpread. With glibc's dynamic mmap threshold disabled it takes
\AudAllocFixedLo--\AudAllocFixedHi\,ms in every mode, a factor of \AudAllocFixedSpread, and the
throughput spread between modes falls from \AudAllocDefaultThrSpread\,\% to
\AudAllocFixedThrSpread\,\%. The stage time is thus governed by where the 1\,MiB chunk buffer is
allocated, which depends on a mode's earlier allocations, and not by the cipher or the key
establishment. A small residual for X-Wing remains.
The residual for X-Wing is not explained, and the diagnostic was exploratory.

\section{Security--Performance Trade-off}\label{sec:tradeoff}
\subsection{What a Session Exposes}
In P1 every object has its own shared secret, and an attacker who obtains one learns one object.
In N1 the unit of compromise is the session root: whoever reads a root from process memory, a
crash dump, a swap file or a log can derive the data keys of every object it protected, at most
$B_{\max}$ objects written within $T_{\max}$ seconds. A cache shared between tenants would extend
that exposure across tenants, so roots must be scoped to one recipient key, as ours are. This
exposure is distinct from, and much smaller than, compromise of the recipient's long-term
decapsulation key, which exposes all objects in every mode. The theoretical $1/B_{\max}$
operations per object holds only when sessions fill before the time limit, so we report what was
observed.

\subsection{Measured Trade-off}

$T_{\max}=1$\,s a root protected a median of \RevSessShortObjects{} objects under closed-loop

\emph{Throughput and tail latency} do not change: in none of the \RevSessConfigs{} configurations
with $B_{\max}\ge 10$ does the throughput interval exclude 1
(\RevSessThroughputLo--\RevSessThroughputHi), because this workload is limited by the server. On a
client-bound workload, 64\,KiB GET at 32 workers, a receiver that caches roots gains
\RevSessGetGain\,\% throughput (95\,\% CI \RevSessGetGainLo--\RevSessGetGainHi\,\%) at
$B_{\max}=100$. This is an upper bound: the run reads 32 objects repeatedly, so every root stays
in the receiver's cache and almost no decapsulation remains; a workload with a large working set
would gain less. The exploratory campaign agrees: N1 saved
\NoneSaveOneMin--\NoneSaveOneMax\,\textmu s of CPU per request at one worker and raised
throughput only for small GETs at 32--128 workers (\NoneGetGainMin--\NoneGetGainMax\,\%). Its
queue-aware variant lowered the bound under light load as designed, re-keying
\QaKemRatioLow$\times$ as often as a fixed bound of 100 at \QaRateLow{} requests/s with no
measurable change in tail latency; we did not show that it is better than a smaller fixed bound.

\subsection{Decision Rule}
The measurements support a conservative rule. Per-object ML-KEM is the default. Amortization is
enabled only for a workload in which profiling shows the client CPU to be the bottleneck, and
then with the smallest bound that achieves the gain: in our data $B_{\max}=10$ already removes
most of the CPU cost, so a larger bound buys exposure without benefit. $T_{\max}$ should be set
from the tolerated exposure of an idle client, since it is the limit that binds under light load.
The same reasoning applies to the choice between ML-KEM and a hybrid: where the client is not the
bottleneck the hybrid costs only \RevMetaXwingOverMLKEM{} bytes per object, and where it is, the
cost is the throughput difference reported in Section~\ref{sec:hybrid}.

\section{Robustness and Validity}\label{sec:validity}
\subsection{Run-to-Run Variation}
Fig.~\ref{fig:tost} shows every paired ratio of the primary family. Six cells are tight: the
coefficient of variation of throughput across runs is at most \RevCvQuietMax\,\%. The two
64\,KiB PUT cells vary by \RevCvNoisyLo--\RevCvNoisyHi\,\% per mode. That variation originates at
the server (Section~\ref{sec:bottleneck}) and affects all modes alike, which is why it widens
intervals without shifting ratios.

\subsection{Stalls}
The pre-registered rule flags \RevStalls{} of \RevRuns{} x86 runs and \ArmStalls{} of \ArmRuns{}
ARM runs, all of them PUTs of at most 64\,KiB. Excluding them leaves the 8 x86 verdicts
unchanged and turns one ARM verdict, the knee cell, from equivalent to inconclusive
(Section~\ref{sec:primary}).

\subsection{Order and Time Effects}
Modes are shuffled within each repetition. As a check, for each primary cell we regress log
throughput on the mode, repetition fixed effects, elapsed time in the experiment, position in the
block and whether the previous run was a PUT. The adjusted P1/B2 ratio differs from the paired
ratio by at most \RevOrderShiftMax\,\% in any cell on either architecture.

\subsection{Second Architecture}
The ARM replication reproduces the pattern: equivalence at 1\,MiB and above, a deficit of
\RevHotDeficit\,\% (x86) and \ArmHotDeficit\,\% (ARM) in the client-bound cell, and noise in small PUT. Because that testbed also has another server
instance, it tests the robustness of the ratios and not ARM against x86 in absolute terms.

\subsection{Threats to Validity}
\textbf{Internal.} Stage timers above one worker include interpreter-lock waiting, so
key-establishment time is reported at one worker only. During the x86 chain of the confirmatory
campaign, completed experiments were downloaded from the client while parts of
\lab{Hybrid-Matrix}, \lab{Sessions} and \lab{Open-Loop} were running; the transfer used client CPU and network and may have added noise to those runs.
Mode order is randomized within repetitions, so it cannot favour a mode, and no transfer
overlapped \lab{Primary-x86} or \lab{Primary-ARM}. Modes differ in manifest size as well as
in key establishment; \lab{Control-Manifest} separates the two for the Python client only
(Section~\ref{sec:mechanism}). Seven of the eight primary cells could not have shown an effect
of the mode on throughput. The exploratory campaign's pause failure
(Section~\ref{sec:method}) added noise to small PUT cells; its results for those cells come from
\lab{Expl-SmallPUT}. The 1\,MiB one-worker slowdown of the hybrids is attributed to the allocator by an exploratory
diagnostic and keeps an unexplained residual (Section~\ref{sec:anomalies}). The profiling
attribution names a subsystem, not a function. The two inconclusive primary cells were
under-powered; \lab{Power-PUT} repeated them on x86 only, so on ARM 64\,KiB PUT at 128 workers
and 64\,KiB GET at 500 workers remain inconclusive. Both controls,
\lab{Control-Manifest} and \lab{Control-Binding}, ran on the x86 client only: the ARM client
uses the same binding and shows a similar deficit, but the attribution to the binding is not
tested there. The line we draw between a saturated and an unsaturated Python cell rests on a
difference of a few tenths of a core, was drawn after the data and was not pre-registered;
anomaly A3 may be a consequence of drawing it too high.

\textbf{External.} These are the limits of what the data supports. Most of the study uses one
Python client with liboqs through a binding, and \lab{Control-Binding} shows how much that instrument can
shape a result: its one client-bound deficit was produced by the binding. The native reader
removes the interpreter but covers only the GET path of three modes at one object size, uses
different cryptographic implementations, and reaches saturation only when confined to one core,
which is an artificial condition; a production client saturating many cores may behave
differently. The baseline set is narrow: no ML-KEM-1024, no RSA-3072, and no remote
key-service wrap, which is a common deployment path. MinIO ran as a single node without erasure
coding or replication, in a community edition that is no longer developed; a distributed
deployment has a different write path and may have a different ceiling and knee. Both hosts sat
in one placement group with a sub-millisecond round trip; a wide-area client would be dominated
by the network. All runs used AWS, in two regions, with one server instance type. liboqs is
intended for prototyping, not production.

\textbf{Construct.} Throughput equivalence within $\pm$5\,\% is an engineering criterion, not a
statement that two modes are identical; a ratio of \RevHotRatio{} with a narrow interval is
formally equivalent and still a real difference. The CPU accounting is an identity on the runs
it describes; in the native reader it holds by construction; its one advance prediction missed
by up to \AudPredictionErrorL{} points and lay outside both intervals. The statement that a
throughput cost appears only at or near client saturation is contradicted by anomaly A2 if
``saturation'' is read strictly, and the Python client's process CPU and the native reader's
are not measured the same way (thread CPU at 500 workers against process CPU on one core), so
their per-request figures should not be compared as like for like. The exploratory verdict counts are not corrected for
multiplicity. Runs last 20\,s; slower effects such as compaction or long-term memory growth are
not observed.

\subsection{Experiments Still Required}\label{sec:pending}
The following have not been run, and the paper's claims are limited accordingly.
(1)~\emph{A full native client:} PUT, the remaining modes and several object sizes, saturating
many cores, with a second ML-KEM implementation so that library and language can be separated.
(2)~\emph{A manifest control in the native reader}, to split its ML-KEM cost into key recovery
and manifest handling by measurement and not by a separate timing.
(3)~\emph{An HPKE-conformant envelope}, to confirm that the per-object costs transfer.
(4)~\emph{Wider baselines:} ML-KEM-1024, RSA-3072 and a remote key-service wrap.
(5)~\emph{A distributed or second S3 implementation}, and runs of 10 to 30 minutes, for the
store-side results.
(6)~\emph{The two controls on the ARM client.}

\section{Discussion}\label{sec:discussion}
\textbf{What a practitioner learns beyond the estimate.} That tens of microseconds of KEM are
small against milliseconds of storage is true but incomplete. Three things could not have been
read off that estimate. First, the regime in which a cost appeared is narrow and identifiable:
a client at or near CPU saturation, with the size of the cost given by client CPU per request.
Second, the first cause we suspected was wrong. The 1{,}088-byte ciphertext and its handling
explain \AudPadShare\,\% of the x86 Python client's deficit; the rest came from a binding that
crosses into native code four times per decapsulation. Third, the size of the effect depends on
the library: the ML-KEM operation was cheaper than an X25519 exchange with liboqs called
directly and dearer in Go's standard library, and the throughput cost under saturation ranged
accordingly from equivalence within $\pm$2\,\% to \AudNOneMlkemDeficit\,\%. In no saturated cell
was ML-KEM faster than X25519.

\textbf{Migration planning.} The CPU accounting of Section~\ref{sec:cpumethod} gives a short
procedure. Measure client CPU per request for the current and the candidate mode on the real
workload and client. If clients are well below CPU saturation, our data gives no reason to
expect a change in throughput, with the reservation of anomaly A2. If they are saturated, expect
throughput to change by about the inverse ratio of the two CPU figures:
\RevHotDeficit--\ArmHotDeficit\,\% in our Python client, \AudNOneMlkemDeficit\,\% in our native
reader on one core, and equivalence within $\pm$2\,\% with a one-call binding on x86. A
measurement on one client stack does not transfer to another.

\textbf{For library authors.} A binding that allocates an object and makes several foreign calls
per operation can cost more under thread contention than the cryptography it wraps. In our x86
client, holding a handle per process and making one call per operation removed
\AudBindReleasedRemoved\,\% of the deficit (90\,\% CI
\AudBindReleasedRemovedLo--\AudBindReleasedRemovedHi\,\%); whether that call released the
interpreter lock made no measurable difference.

\textbf{Where the cost lies.} The cost that does not depend on the implementation is ML-KEM's
1{,}088-byte ciphertext: \RevMetaIntrinsic{} bytes more per object than an X25519 key, or
\RevMetaExtraMLKEM{} more in a JSON/base64 manifest, which puts such a manifest at or above the
2\,KB that Amazon S3 allows for user-defined metadata (Section~\ref{sec:metadata}). For hybrids
there is in addition a client-CPU increment under saturation. RSA-4096 is the poor choice: its
private-key operation makes small-object reads CPU-bound at \RevRsaGetLo--\RevRsaGetHi{} of
ML-KEM's throughput in the Python client.

\textbf{Capacity of the store.} The open-loop measurements are reported in the supplementary
material because they describe the store and not post-quantum cryptography. Their result is that
mean response time doubles at \RevQMidRhoKneeLo--\RevQSmallRhoKneeHi{} of peak closed-loop
throughput, in line with the known gap between closed- and open-loop
behaviour~\cite{schroeder2006}; the exploratory campaign found that knee in the same place for
the symmetric-only mode and for ML-KEM.

\section{Conclusion}\label{sec:conclusion}
We evaluated per-object post-quantum key establishment on an S3-compatible store with a Python
client on x86 and ARM and with a native Go reader, against a single-node MinIO server on AWS. In
these configurations ML-KEM lowered throughput against X25519 only where the client was at or
near CPU saturation, with one unexplained exception in the native reader
(Section~\ref{sec:anomalies}). In the one saturated cell of the pre-registered family the
Python client was \RevHotDeficit\,\% (x86) and \ArmHotDeficit\,\% (ARM) slower; two
pre-registered controls on x86 attribute that deficit to the library binding and
\AudPadShare\,\% of it to the larger manifest, and with one foreign call per operation ML-KEM was
equivalent to X25519 within $\pm$2\,\%. A native reader saturated on one core was
\AudNOneMlkemDeficit\,\% slower with ML-KEM and \AudNOneXwingDeficit\,\% with X-Wing; a slower
key recovery in its library accounts for about half of the extra CPU for ML-KEM and about three
quarters for X-Wing. In the saturated cells the throughput loss matched the extra client CPU per
request, which makes CPU per request the quantity to measure before a migration. The size of
the cost depends on the client implementation. The cost that every implementation pays is
storage: \RevMetaIntrinsic{} bytes more per object than X25519.

These results describe two clients, one single-node store and one cloud provider, and the
native reader covers the GET path only. They should not be extended to distributed object
stores, other S3 implementations, other libraries or wide-area deployments without new
measurements (Sections~\ref{sec:pending} and~\ref{sec:planned}).
