\title{Benchmarking Post-Quantum Key Encapsulation in S3-Compatible Object Storage under Client Concurrency}

\author{\IEEEauthorblockN{Team 12 (author names to be added)}

\begin{abstract}
Large-scale quantum computers would break the RSA and elliptic-curve key establishment that
protects most encrypted cloud data, and ciphertext stored today can be decrypted later. NIST
standardized ML-KEM (FIPS~203) as the replacement key-encapsulation mechanism, but its cost has
mostly been measured in isolation or inside TLS handshakes, not in the per-object encryption
path of cloud object stores under concurrent load. We build an instrumented client-side
envelope-encryption layer for an S3-compatible store (MinIO) in which every object is protected
by ML-KEM-768, HKDF-SHA256 and chunked AES-256-GCM, and compare it on one data path with no
encryption, symmetric-only encryption, RSA-OAEP-4096, X25519 and a hybrid X25519+ML-KEM-768
mode, from 1 to 500 concurrent workers and from 1\,KiB to 500\,MiB objects, on two dedicated
cloud hosts (\TotalRuns{} runs, \TotalRequestsM{} million measured requests, \TotalFailures{}
failures). ML-KEM-768 costs \HsPutPone\,ms per PUT and \HsGetPone\,ms per GET, at most
\KeShareSmallGet\,\% of request time even for 1\,KiB objects. In \HoneEquiv{} of \HoneCells{}
paired comparisons its throughput is statistically equivalent to X25519 within $\pm$5\,\%,
and \HoneDiff{} differ by more. Every mode reaches the same network, storage or client-CPU ceiling, except
RSA-4096, whose \HsGetRone\,ms decryption saturates the client and cuts small-object GET
throughput to \RoneGetThrMin--\RoneGetThrMax{} of ML-KEM's. Bounded session amortization of
ML-KEM saves \NoneSaveMinUs--\NoneSaveMaxUs\,\textmu s of client CPU per request, which raises
throughput only where the client is the bottleneck. Open-loop load shows a sharp knee between
\(\rho=\QSmallKneeLo\) and \(\QSmallKneeHi\) that an M/M/c model does not predict.
\end{abstract}

\section{Introduction}
Cloud object stores keep data for years. An adversary who records encrypted objects or
key-exchange traffic today can decrypt them once a cryptographically relevant quantum computer
exists (``harvest now, decrypt later''). The standard response is to replace RSA and
elliptic-curve key establishment with post-quantum key-encapsulation mechanisms. In August 2024
NIST published FIPS~203, standardizing ML-KEM (derived from CRYSTALS-Kyber) and recommending
ML-KEM-768 as the default parameter set~\cite{fips203}.

For object storage the question is practical. Every object stored with client-side envelope
encryption needs its own key establishment, a larger metadata record and more client CPU.
Whether this matters depends on object size, the operation and how many clients compete for
the same CPUs, network and storage servers. Prior measurements concentrate on algorithm
micro-benchmarks and TLS handshakes; cloud-storage proposals evaluate security properties and
single-client encryption time (\S\ref{sec:related}).

We ask three questions. \textbf{RQ1:} What does per-object ML-KEM-768 add to latency,
throughput, CPU and memory, compared with RSA-4096, X25519 and symmetric-only baselines on the
same data path? \textbf{RQ2:} How does this change with object size and with 1--500 concurrent
workers? \textbf{RQ3:} Can a queueing model predict where response time degrades, and can
bounded session amortization of ML-KEM move that point?

\textbf{Contributions.} (i) An instrumented, reproducible benchmark of per-object ML-KEM-768
envelope encryption on an S3-compatible store with six key-establishment modes on one data
path, stage-level latency decomposition, client and server resource sampling and streaming
memory for objects of hundreds of MiB. (ii) A measurement on two dedicated cloud hosts with
five randomized repetitions per configuration, paired within-batch comparisons and explicit
equivalence tests. (iii) An evaluation of bounded session amortization of ML-KEM, including a
variant whose bound follows client utilization. Bounded key reuse itself is established
practice (\S\ref{sec:related}); our claim is its application to ML-KEM roots, its quantified
trade-off, and the queue-aware variant as a candidate policy. (iv) The artifact, whose
validator refuses data with inconsistent timers, checksums or session bounds.

\section{Background}
\textbf{ML-KEM.} A KEM has three algorithms: key generation, encapsulation (which, given the
recipient's public key, outputs a ciphertext and a 32-byte shared secret) and decapsulation.
ML-KEM-768 targets NIST security category~3, with a 1{,}184-byte encapsulation key, a
2{,}400-byte decapsulation key and a 1{,}088-byte ciphertext~\cite{fips203}. Decapsulation uses
\emph{implicit rejection}: a modified ciphertext or a wrong key yields a pseudorandom secret
instead of an error, so tampering is detected by the authenticated encryption that follows.

\textbf{Envelope encryption.} A per-object data key encrypts the object; key establishment
protects that data key for the recipient. We derive keys with HKDF-SHA256~\cite{rfc5869} and
encrypt with AES-256-GCM, which requires nonce uniqueness per key~\cite{sp80038d}.

\textbf{Object stores.} S3-compatible stores expose PUT and GET of whole objects. We use
MinIO~\cite{minio}. Its community edition was archived in 2026 and no longer publishes images,
so we compile the final community release (\MinioRelease) from source; because all
cryptography is client-side, any S3-compatible store can be substituted.

\section{Related Work}\label{sec:related}
\textbf{Algorithm-level cost.} Library benchmarks such as those in liboqs~\cite{liboqs} and
comparative studies of ML-KEM against RSA and ECC~\cite{rodriguez2025} quantify key
generation, encapsulation and decapsulation and the larger key and ciphertext sizes. They do
not include storage, concurrency or end-to-end request latency.

\textbf{Transport security.} Hybrid key exchange in TLS~1.3~\cite{rfc8446}, with combiners
such as X-Wing~\cite{xwing}, protects data in transit; session resumption amortizes the
handshake across connections. Our work concerns keys protecting data at rest, one per object,
and holds transport security constant.

\textbf{Post-quantum cloud storage.} Prikutse et al.~\cite{prikutse2026} combine AES-256-GCM,
X25519+ML-KEM-768 and ML-DSA-65 for multi-file cloud storage and amortize signatures by batch
commitment. According to its abstract, that evaluation does not cover an S3 store, concurrent
clients or queueing behaviour.

\textbf{Bounded key reuse.} Amazon S3 Bucket Keys derive per-object data keys from a
time-limited bucket-level key and reduce key-service requests by up to
99\%~\cite{s3bucketkeys}; the AWS Encryption SDK caches data keys with age and message-count
limits~\cite{esdkcache}. Our session mode applies the same principle to ML-KEM-established
roots in client-side encryption. We found no prior load-adaptive bound.

\section{Threat Model and Design}
\textbf{Threat model.} The network and object store are honest-but-curious for confidentiality
and potentially malicious for integrity: an adversary may read, replace, delete, reorder or
replay stored ciphertexts and manifests. The adversary does not hold the recipient's
decapsulation key. Availability, traffic analysis and side channels in the Python client are
out of scope.

\textbf{Construction (mode P1).} For object identity
$I=(\mathit{tenant},\mathit{bucket},\mathit{key},\mathit{version})$ the client computes
$(C,S)\leftarrow\mathrm{Encaps}(ek)$ and
$K\leftarrow\mathrm{HKDF}(S,\mathit{salt},\text{``pqc-s3-object-v2''}\|0\|\mathit{ctx})$, where
$\mathit{ctx}$ is canonical JSON of $I$, the mode, algorithm names, chunk size, chunk count,
plaintext size, recipient key identifier and a hash of $C$. The object is split into 4\,MiB
chunks; chunk $j$ uses nonce $p\|\mathrm{be}_{64}(j)$ with a random 32-bit prefix $p$ and
associated data $\mathit{ctx}\|j\|\ell_j\|\mathit{final}_j$. Deletion, reordering, truncation,
extension and cross-object splicing therefore fail authentication. The ciphertext is uploaded
first and a manifest holding $\mathit{ctx}$, $C$, the salt and the prefix is written last as
the commit record, so an interrupted upload is never visible. Object versions are time-ordered
UUIDv7 values.

\textbf{Comparison modes.} All encrypting modes share the HKDF and chunked AES-GCM path: B0
stores plaintext through the same framing (storage and harness cost); B1 derives keys from a
pre-shared 32-byte key; R1 transports a random 32-byte secret with
RSA-OAEP-4096~\cite{rfc8017}; B2 uses ephemeral-static X25519~\cite{rfc7748}; P2 concatenates
X25519 and ML-KEM-768 secrets. A reader must name the mode it expects, so a planted plaintext
object cannot downgrade P1.

\textbf{Bounded sessions (mode N1).} One encapsulation yields a root $S_r$; object $i$ uses
$K_i=\mathrm{HKDF}(S_r,\mathit{salt}_i,\text{``pqc-s3-session-v1''}\|0\|\mathit{ctx}_i)$, with
the session identifier, the object's sequence number and the bound authenticated in
$\mathit{ctx}_i$. A root protects at most $B$ objects and lives at most $T_{\max}$ seconds. In
the queue-aware variant,
$B_t=\mathrm{clip}(B_{\min},B_{\max},\mathrm{round}(B_{\min}+(B_{\max}-B_{\min})\hat\rho))$
with $\hat\rho$ an exponentially weighted estimate of the fraction of busy worker threads:
under light load a root is used for fewer objects. $B_t$ is fixed per session, so $B_{\max}$
and $T_{\max}$ are hard caps. A leaked root exposes at most $B_{\max}$ objects; compromise of
the recipient's decapsulation key exposes all objects in both P1 and N1. Receivers cache
decapsulated roots under their own caps and reject objects whose authenticated sequence number
exceeds them.

\section{Implementation}
The client is Python~\PythonVersion{} using liboqs~\LiboqsVersion{} through liboqs-python
\LiboqsPyVersion~\cite{liboqs,liboqspython}, built from a pinned release with only ML-KEM
enabled, pyca/cryptography~\CryptographyVersion~\cite{pyca} for HKDF, AES-GCM, RSA and X25519,
and the MinIO Python SDK \MinioPyVersion. A test checks ML-KEM interoperability with an
independent implementation (OpenSSL via pyca) in both directions. Storage is streamed: objects
are encrypted chunk by chunk and uploaded in 8\,MiB parts, so memory stays bounded regardless
of object size. A multi-process runner realizes $N$ concurrent workers as exactly $N$ threads
over $\min(N,16)$ processes that start together after warm-up. It records every request,
including failures, with stage timers (key establishment, key derivation, AES-GCM, manifest
handling and storage), and samples client resources and MinIO's own process metrics once per
second. A validator rejects a data set if checksums fail, a record deviates from the schema,
any request's stage times exceed its total, a run's 99th-percentile unaccounted time exceeds
2\,\%, or an N1 session exceeds its bound. The test suite has over two hundred tests, including
tamper, replay, downgrade and session-bound stress tests.

\section{Methodology}\label{sec:method}
\textbf{Testbed.} Two dedicated AWS instances in one cluster placement group (\Region): the
client on a \ClientType{} (\ClientCPU, \ClientVCPU{} vCPU, \ClientRAMGiB\,GiB) and MinIO, single
node in Docker with host networking, on an \ServerType{} (16 vCPU, local NVMe). Baselines
before the runs: \LinkGbit\,Gbit/s (\LinkMiB\,MiB/s) between the hosts with iperf3, a
\RTTms\,ms round trip, and \FioReadMiB\,MiB/s read and \FioWriteMiB\,MiB/s write on the MinIO
disk with fio. Code at commits \Commits.

\textbf{Workload.} PUT and GET are measured separately in a closed loop (each worker issues
its next request when the previous one completes), with 5\,s warm-up and 20\,s measured per
run and fresh worker processes for every run. Concurrency 1--500 is measured at 64\,KiB and
1\,MiB; 16\,MiB stops at 128 workers because 500 objects of 16\,MiB in flight exceed the
client's memory; object size 1\,KiB--500\,MiB is measured at one worker, with 128\,MiB at 32
and 500\,MiB at 16 workers. Large objects require at least 10 measured operations per run.
For RQ3, an open-loop generator offers Poisson arrivals of 1\,KiB and 64\,KiB PUTs, served by
256 threads, at rates around the measured capacity. N1 is measured at
$B_{\max}\in\{10,100,1000\}$, $T_{\max}=60$\,s, and the queue-aware variant at
$B_{\min}=1$, $B_{\max}=100$.

\textbf{Replication and statistics.} Every configuration runs five times; the order of modes
is shuffled within each repetition. A run is the unit of analysis: we report the mean over
runs with a Student-$t$ 95\,\% interval. Modes are compared only within one batch, paired by
repetition, as the ratio $\exp(\overline{\log(x_a/x_b)})$ with a $t$-interval; a comparison is
\emph{equivalent} if its whole interval lies within $\pm$5\,\%, \emph{different} if it lies
entirely outside, and \emph{inconclusive} otherwise. Above one worker, stage timers include
time spent waiting for the Python interpreter lock, so we report key-establishment cost and
stage shares at one worker and client CPU as thread CPU time per request.

\textbf{Batches.} The study ran in four batches (Table~\ref{tab:sources}). In batches A--C the
pause between runs, meant to wait until MinIO stopped writing, fell back to 5\,s because
MinIO in Docker does not export its disk-write counter. A PUT run that followed another PUT run
was then sometimes slowed by \StallSlowMin--\StallSlowMax\,\%, consistent with the previous run's writeback and
object purge still in progress: \NoisySmallPutABC{} small-object PUT cells exceeded our 5\,\%
limit on run-to-run variation and \StallsABC{} runs were flagged as stalls. Because mode order
was shuffled, this added noise but no bias. Batch D re-measured all PUT cells up to 64\,KiB
with a 40\,s pause, covering the kernel's 30\,s dirty-page writeback and MinIO's 5\,s cleanup
interval: the variation of P1 at 64\,KiB and 128 workers fell from \CVBeforePone\,\% to
\CVAfterPone\,\% (B1: \CVBeforeBone\,\% to \CVAfterBone\,\%), with \StallsD{} stalls in
\RunsD{} runs. Batch D is the result of record for those cells.

\textbf{Handshake overhead (RQ1).} Table~\ref{tab:handshake} gives key-establishment time per
request. ML-KEM-768 costs \HsPutPone\,ms to encapsulate on PUT and \HsGetPone\,ms to
decapsulate on GET. X25519 costs \HsBtwoOverPonePut$\times$ more on PUT, where the sender
generates an ephemeral key, and about the same on GET. RSA-4096 is cheap to encrypt but costs
\HsGetRone\,ms to decrypt, \HsRoneOverPoneGet$\times$ ML-KEM decapsulation, which places its
cost on the read path. The price of ML-KEM is metadata: its manifest is \ManifestPone\,bytes
against \ManifestBtwo{} for X25519 and \ManifestRone{} for RSA-4096, because it carries the
1{,}088-byte ciphertext.

\textbf{Hybrid mode.} P2 (X25519+ML-KEM-768) is equivalent to P1 in \PtwoEqCount{} of
the \PtwoCells{} cells at 1\,MiB from 8 workers on. At one worker its PUT throughput is
\PtwoPutOnePct\,\% lower. Most of that gap, like the higher cost of B1 at the same size, sits
in the AES-GCM stage (\AeadPtwoMid\,ms for P2 and \AeadBoneMid\,ms for B1 against
\AeadPoneMid\,ms for P1), although all modes run the identical cipher code: it arises outside
the cipher and we did not isolate its cause. At 1\,MiB we therefore use B0 and B2, not B1, as
references.

\textbf{Bounded sessions.} With a bound $B_{\max}$, N1 performed one ML-KEM operation per
$B_{\max}$ objects (\NoneKemPerReqHundred{} per request at $B_{\max}=100$), as designed and
as the validator checked for every session. Fig.~\ref{fig:n1} shows the effect. N1 saves
\NoneSaveMinUs--\NoneSaveMaxUs\,\textmu s of client CPU per request against P1. Because ML-KEM is
a small part of every request, this is visible as throughput only where the client CPU is the
bottleneck: small GETs at 32--128 workers (client CPU \NoneGetClientPct\,\%) run
\NoneGetGainMin--\NoneGetGainMax\,\% faster. On PUT, where MinIO limits throughput, N1 is
equivalent to P1 in \NonePutEquiv{} of \NonePutCells{} cells and inconclusive in the rest. The
queue-aware variant adapts as intended: under open-loop load of \QaRateLow{} and \QaRateMid{}
requests/s its mean bound was \QaBoundLow{} and \QaBoundMid, so it re-keyed
\QaKemRatioLow$\times$ and \QaKemRatioMid$\times$ as often as the fixed bound of 100, with a
99th-percentile response-time ratio of \QaPninetyRatioLow{} [\QaPninetyLoLow,
\QaPninetyHiLow] and \QaPninetyRatioMid{} [\QaPninetyLoMid, \QaPninetyHiMid]; under overload
its bound rose to \QaBoundSat. This shows that the policy works at no measurable cost; it does
not show that it is better than a smaller fixed bound.

\textbf{Queueing (RQ3).} Fig.~\ref{fig:queue} shows mean response time (queue wait plus
service) against offered load $\rho=\lambda/\mu$, with capacity $\mu$ taken from the most
overloaded runs (\QSmallCap{} requests/s at 1\,KiB, \QMidCap{} at 64\,KiB). We model the
system as M/M/c with $c=\mu S_0$ servers, where $S_0$ is the service time at light load
(\QSmallSzero\,ms; $c=\QSmallServers$ at 1\,KiB, \QMidServers{} at 64\,KiB). Below the knee the
model is within \QSmallStableErrPct--\QMidStableErrPct\,\% of the measurements. It misses the
knee: at 1\,KiB and \QSmallKneeRate{} requests/s ($\rho=\QSmallKneeHi$) it predicts
\QSmallPredKnee\,ms while the system was already unstable, with mean response above
\QSmallMeasKnee\,ms; at 64\,KiB the same happens at $\rho=\QMidKneeHi$ (predicted
\QMidPredKnee\,ms, measured above \QMidMeasKnee\,ms). The knee lies between
$\rho=\QSmallKneeLo$ and \QSmallKneeHi{} at 1\,KiB and between \QMidKneeLo{} and \QMidKneeHi{}
at 64\,KiB, for B1 and P1 alike. The model fails because service time is not independent of
load: the median service time of a 1\,KiB PUT rises from \QSmallSvcLow\,ms at light load to
about \QSmallSvcHigh\,ms in overload, as concurrent writes contend inside MinIO. Usable
capacity is therefore between \QMidKneeLo{} and \QSmallKneeHi{} of the saturation throughput,
and ML-KEM does not move it.

\section{Discussion}
For per-object envelope encryption on an S3-compatible store, ML-KEM-768 is not a performance
problem. Its key establishment costs tens of microseconds, less than X25519 on PUT in our
stack, and disappears against the milliseconds of storage round trips; on every workload we
measured, throughput is set by the network, by MinIO's write path or, for small GETs, by the
client CPU, and ML-KEM reaches those limits together with the classical modes. The
measurable costs of migration are elsewhere: \ManifestExtraPone{} more bytes of metadata per object
than X25519, which
matters for very small objects and for object-count-based billing, and a few tens of
microseconds of client CPU per request, which matters only when the client is saturated. RSA-4096,
in contrast, is a poor baseline to stay on: its private-key operation makes small-object reads
CPU-bound at \RoneGetThrMin--\RoneGetThrMax{} of the throughput of ML-KEM. Session amortization is useful
exactly where the client CPU is the bottleneck; elsewhere it trades compromise scope for no
measurable gain. For capacity planning, the open-loop results matter more than any
cryptographic choice: response time collapses well before nominal saturation.

\section{Threats to Validity}
\textbf{Internal.} The pause between runs failed in batches A--C (\S\ref{sec:method}); batch D
repeated the affected cells with a working pause, but \NoisyD{} of its \CellsD{} cells still
exceed 5\,\% variation. Absolute small-object throughput differed by up to \BatchDriftPct\,\% between
batches, so all comparisons are within one batch. Stage timers above one worker include
interpreter-lock waiting. Five repetitions give $t$-intervals with four degrees of freedom; the
attribution of the small-PUT limit to MinIO's write path is by elimination, and the AES-GCM
cost difference between modes at 1\,MiB is unexplained. \textbf{External.} The client is
Python, so absolute costs include interpreter overhead and differ from native or
hardware-accelerated implementations; MinIO ran as a single node without erasure coding;
results describe one instance pair in one region. liboqs is intended for prototyping, not
production. \textbf{Construct.} ``Handshake overhead'' is per-object key establishment, not a
network handshake; transport security was held constant.

\section{Conclusion}
We built and validated an instrumented, reproducible benchmark of post-quantum envelope
encryption for S3-compatible object storage and measured it from 1 to 500 concurrent workers
and from 1\,KiB to 500\,MiB objects on dedicated cloud hosts. ML-KEM-768 adds
\HsPutPone--\HsGetPone\,ms per object, is statistically equivalent to X25519 within $\pm$5\,\%
in \HoneEquiv{} of \HoneCells{} comparisons, with \HoneDiff{} differing by more, while RSA-4096
limits small-object reads to \RoneGetThrMin--\RoneGetThrMax{} of ML-KEM's throughput. Bounded session amortization helps only when
the client CPU is the bottleneck, and a queueing model with load-independent service time does
not predict where response time collapses.
