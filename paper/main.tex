\begin{abstract}
Large-scale quantum computers would break the RSA and elliptic-curve key establishment that
protects most encrypted cloud data, and ciphertext stored today can be decrypted later. NIST
standardized ML-KEM (FIPS~203) as the replacement key-encapsulation mechanism, but its cost has
mostly been measured in isolation or inside TLS handshakes, not in the per-object encryption
path of cloud object stores under concurrent load. We design and implement an instrumented
client-side envelope-encryption layer for an S3-compatible store (MinIO) in which every object
is protected by ML-KEM-768, HKDF-SHA256 and chunked AES-256-GCM, and compare it on one data path
with no encryption, symmetric-only encryption, RSA-OAEP-4096, X25519 and a hybrid
X25519+ML-KEM-768 mode, from 1 to 500 concurrent workers and from 1\,KiB to 500\,MiB objects, on
two separate cloud instances (\TotalRuns{} runs, \TotalRequestsM{} million measured requests,
\TotalFailures{} failures). ML-KEM-768 costs \HsPutPone\,ms per PUT and \HsGetPone\,ms per GET,
at most \KeShareMax\,\% of request time even for the smallest objects. In \HoneEquiv{} of
\HoneCells{} paired comparisons its throughput is statistically equivalent to X25519 within
$\pm$5\,\%, and none is confirmed to differ by more (\HoneInconc{} are inconclusive). Every mode
reaches the same network, storage or client-CPU ceiling, except RSA-4096, whose \HsGetRone\,ms
decryption saturates the client and cuts small-object GET throughput to
\RoneGetThrMin--\RoneGetThrMax{} of ML-KEM's. Bounded session amortization of ML-KEM saves
\NoneSaveOneMin--\NoneSaveOneMax\,\textmu s of client CPU per request at one worker and up to
\NoneSaveConcMax\,\textmu s under contention, which raises throughput only where the client is
the bottleneck. Open-loop load shows a sharp knee between \(\rho=\QMidKneeLo\) and
\(\QSmallKneeHi\) that an M/M/c model does not predict.
\end{abstract}

\section{Introduction}
Cloud object stores keep data for years, and much of that data is encrypted under keys
established with RSA or elliptic-curve Diffie--Hellman. Shor's algorithm would allow a
sufficiently large quantum computer to recover those keys, so an adversary who records
ciphertext today can decrypt it once such a machine exists, a threat usually called
``harvest now, decrypt later''. For data at rest the exposure lasts as long as the data is
retained, which makes storage an early candidate for migration. In August 2024 NIST published
FIPS~203, standardizing the module-lattice key-encapsulation mechanism ML-KEM and recommending
ML-KEM-768 as its default parameter set~\cite{fips203}.

Moving object storage to ML-KEM is not a drop-in change. With client-side envelope encryption,
every object needs its own key establishment, so the cost of the KEM is paid on every PUT and
every GET rather than once per connection. Migration raises three practical questions:
(a) the CPU cost of encapsulation and decapsulation per request; (b) the larger key-establishment
ciphertext, which must be stored with every object; and (c) the interaction of both with
concurrency, where many clients share CPUs, the network and the storage servers. Earlier
performance studies of post-quantum cryptography concentrate on algorithm micro-benchmarks and
on TLS connection establishment~\cite{paquin2020,sikeridis2020}, where the cost is amortized over a
session; performance studies of the S3 interface, in turn, do not include
cryptography~\cite{gadban2021}. To our knowledge, the per-object path of an object store under
concurrent load has not been measured.

In this paper, we measure what per-object ML-KEM-768 costs an S3-compatible object store and
when that cost becomes visible. We ask three research questions. \textbf{RQ1:} What does
per-object ML-KEM-768 add to latency, throughput, CPU and memory, compared with RSA-4096, X25519
and symmetric-only baselines on the same data path? \textbf{RQ2:} How does this change with object
size and with 1--500 concurrent workers? \textbf{RQ3:} Can a queueing model predict where
response time degrades, and can bounded session amortization of ML-KEM move that point?

The \textbf{key contributions} of this work are as follows:
\begin{enumerate}
\item We design a client-side envelope-encryption layer for S3-compatible stores with seven interchangeable key-establishment modes on one data path, chunked authenticated encryption
bound to the object's identity, and a commit protocol that never exposes partial uploads
(Section~\ref{sec:design}).
\item We implement it, together with a measurement harness that decomposes every request into
key establishment, key derivation, encryption, metadata and storage time, samples client and
server resources, and refuses inconsistent data; and we automate a two-host cloud testbed
(Section~\ref{sec:impl}).
\item We report a measurement of \TotalRuns{} runs with five randomized repetitions per
configuration, paired within-batch comparisons and explicit equivalence tests, covering
handshake overhead, throughput, CPU and memory (Section~\ref{sec:results}).
\item We evaluate bounded session amortization of ML-KEM, including a variant whose bound follows
client utilization, and test an M/M/c model against open-loop measurements.
\end{enumerate}

Our \textbf{key findings} are:
(i) ML-KEM-768 costs \HsPutPone\,ms per PUT and \HsGetPone\,ms per GET, less than X25519 on PUT and about \HsRoneOverPoneGet{} times cheaper than RSA-4096 decryption on GET;
(ii) its throughput is equivalent to X25519 within $\pm$5\,\% in \HoneEquiv{} of \HoneCells{}
comparisons, because every workload is limited by the network, the storage server or the client
CPU, not by the KEM;
(iii) RSA-4096 is the one mode that changes the bottleneck, limiting small-object reads to
\RoneGetThrMin--\RoneGetThrMax{} of ML-KEM's throughput;
(iv) the measurable price of ML-KEM is \ManifestExtraPone{} more bytes of metadata per object than
X25519; and
(v) response time collapses well before nominal saturation, a knee that an M/M/c model with
load-independent service time does not predict.

\textbf{Scope.} We do not evaluate the security of ML-KEM itself, side channels of the
implementation, or transport security, which we hold constant. Bounded key reuse is established
practice (Section~\ref{sec:related}); our claim for session amortization is its application to ML-KEM
roots, its quantified trade-off, and the queue-aware variant as a candidate policy.

\section{Background}\label{sec:background}
\subsection{Key-Encapsulation Mechanisms and ML-KEM}
A key-encapsulation mechanism (KEM) consists of three algorithms: key generation; encapsulation,
which takes the recipient's public (encapsulation) key and outputs a ciphertext and a shared
secret; and decapsulation, which recovers the shared secret from the ciphertext with the private
(decapsulation) key. ML-KEM, derived from CRYSTALS-Kyber, bases its security on the hardness of
the module learning-with-errors problem. ML-KEM-768 targets NIST security category~3 with a
1{,}184-byte encapsulation key, a 2{,}400-byte decapsulation key, a 1{,}088-byte ciphertext and a
32-byte shared secret~\cite{fips203}. Decapsulation uses \emph{implicit rejection}: a modified
ciphertext or a wrong key yields a pseudorandom secret instead of an error, so tampering is
detected by the authenticated encryption that follows.

\subsection{Envelope Encryption}
In envelope encryption a per-object data key encrypts the object, and key establishment protects
that key for the recipient. We derive data keys with HKDF-SHA256~\cite{rfc5869} and encrypt with
AES-256-GCM, whose security requires that a nonce is never reused under the same
key~\cite{sp80038d}. The classical alternatives for key establishment are key transport with
RSA-OAEP~\cite{rfc8017} and ephemeral-static Diffie--Hellman such as X25519~\cite{rfc7748}.

\subsection{S3-Compatible Object Storage}
Object stores expose a flat namespace of buckets and keys through HTTP operations, most
importantly PUT and GET of whole objects; large objects are uploaded in parts. The S3 interface
has become the de facto standard, and many systems implement it~\cite{gadban2021}. We use
MinIO~\cite{minio}. Its community edition was archived in 2026 and no longer publishes images,
so we compile the final community release (\MinioRelease) from source; because all cryptography
is client-side, any S3-compatible store can be substituted.

\subsection{Queueing Model}
An M/M/c queue has Poisson arrivals at rate $\lambda$, $c$ identical servers and exponentially
distributed service times with mean $S$~\cite{harchol2013}. With offered load $a=\lambda S$ and
utilization $\rho=a/c$, the probability that an arrival must wait is given by the Erlang~C
formula $C(c,a)$, and the mean response time is $W=S+C(c,a)\,S/(c-a)$ for $\rho<1$. We use this
model in RQ3 to ask whether response time under open-loop load can be predicted from the
capacity and the light-load service time alone.

\section{Related Work}\label{sec:related}
\textbf{Algorithm-level cost.} Library benchmarks such as those of liboqs~\cite{liboqs} and
comparative studies of ML-KEM against RSA and elliptic curves~\cite{rodriguez2025} quantify key
generation, encapsulation and decapsulation and the larger key and ciphertext sizes. They do not
include storage, concurrency or end-to-end request latency.

\textbf{Post-quantum TLS.} Paquin et al.~\cite{paquin2020} measure TLS~1.3 connection
establishment with hybrid post-quantum key exchange and signatures under emulated network latency
and packet loss, and Sikeridis et al.~\cite{sikeridis2020} study post-quantum authentication in
TLS~1.3, including its effect on server throughput. Hybrid combiners such as
X-Wing~\cite{xwing} target the same setting. These works concern data in transit, where key
establishment happens once per connection; our work concerns data at rest, where it happens once
per object, and holds transport security constant.

\textbf{Object-storage performance.} Gadban and Kunkel~\cite{gadban2021} analyze the performance
of the S3 interface for HPC workloads and attribute losses to layers of the client stack. Our
harness follows the same principle of separating storage time from client-side cost, applied to
the cryptographic stages.

\textbf{Post-quantum cloud storage.} Prikutse et al.~\cite{prikutse2026} combine AES-256-GCM,
X25519+ML-KEM-768 and ML-DSA-65 for multi-file cloud storage and amortize signatures by batch
commitment. According to its abstract, that evaluation does not cover an S3 store, concurrent
clients or queueing behaviour.

\textbf{Bounded key reuse.} Amazon S3 Bucket Keys derive per-object data keys from a
time-limited bucket-level key and reduce key-service requests by up to 99\%~\cite{s3bucketkeys};
the AWS Encryption SDK caches data keys with age and message-count limits~\cite{esdkcache}. Our
session mode applies the same principle to ML-KEM-established roots in client-side encryption. In
vendor documentation and arXiv we found no prior load-adaptive bound; a search of the academic
databases is still to be completed.

\section{Threat Model and Design}\label{sec:design}
\subsection{Threat Model}
The network and the object store are honest-but-curious for confidentiality and potentially
malicious for integrity: an adversary may read, replace, delete, reorder or replay stored
ciphertexts and manifests. The adversary does not hold the recipient's decapsulation key and may
in the future operate a quantum computer. Availability, traffic analysis and side channels in the
client are out of scope.

\subsection{Key-Establishment Modes}
Table~\ref{tab:modes} lists the seven modes. All encrypting modes share the HKDF and chunked
AES-GCM path, so differences between them isolate the cost of key establishment. B0 stores
plaintext through the same framing and measures the storage and harness cost; B1 derives keys
from a pre-shared 32-byte key and is the symmetric-only floor; R1 transports a random 32-byte
secret with RSA-OAEP-4096; B2 uses ephemeral-static X25519; P1 uses ML-KEM-768; P2 is a hybrid
that stores the ML-KEM ciphertext followed by the X25519 ephemeral key and feeds both 32-byte
secrets to HKDF; and N1 amortizes one ML-KEM encapsulation over a bounded session
(Section~\ref{sec:n1design}). A reader must name the mode it expects, so a planted plaintext object
cannot downgrade P1.

\subsection{Per-Object Envelope and Commit Protocol}
Algorithm~\ref{alg:putget} shows PUT and GET for mode P1. An object is identified by
$I=(\mathit{tenant},\mathit{bucket},\mathit{key},\mathit{version})$, where versions are
time-ordered UUIDv7 values. The context $\mathit{ctx}$ is canonical JSON of $I$, the mode, the
algorithm names, chunk size and count, plaintext size, recipient key identifier and the SHA-256
hash of the key-establishment ciphertext $C$; it is bound into the data key and into every chunk.
Objects are split into 4\,MiB chunks, and chunk $j$ is encrypted with nonce
$p\|\mathrm{be}_{64}(j)$ under a random 32-bit prefix $p$ and associated data
$\mathit{ctx}\|j\|\ell_j\|\mathit{final}_j$, so deletion, reordering, truncation, extension and
cross-object splicing all fail authentication. Each version is stored under
\texttt{key.pqcs/version/} as a ciphertext stream \texttt{data.enc} and a manifest
\texttt{manifest.json} holding $\mathit{ctx}$, $C$, the salt and the prefix. The manifest is
written last and serves as the commit record: readers only consider versions whose manifest
exists, so an interrupted upload is never visible.

\begin{algorithm}[t]
\caption{Per-object PUT and GET (mode P1)}
\label{alg:putget}
\footnotesize
\begin{algorithmic}[1]
\Procedure{Put}{$\mathit{key}, M, ek$}
\State $v \gets \textsc{UUIDv7}()$; \ $I \gets (\mathit{tenant},\mathit{bucket},\mathit{key},v)$
\State $(C,S) \gets \mathrm{ML\mbox{-}KEM.Encaps}(ek)$
\State $\mathit{salt} \xleftarrow{\$} \{0,1\}^{256}$; \ $p \xleftarrow{\$} \{0,1\}^{32}$
\State $\mathit{ctx} \gets \textsc{Canon}(I,\text{mode},n,|M|,\mathrm{id}(ek),\mathrm{H}(C),\dots)$
\State $K \gets \mathrm{HKDF}(S,\mathit{salt},\text{``pqc-s3-object-v2''}\|0\|\mathit{ctx})$
\For{$j \gets 0$ \textbf{to} $n-1$} \Comment{streamed in 8\,MiB parts}
\State $c_j \gets \mathrm{AES\mbox{-}GCM}_K(p\|\mathrm{be}_{64}(j), M_j, \mathit{ctx}\|j\|\ell_j\|\mathit{final}_j)$
\EndFor
\State write $c_0\|\dots\|c_{n-1}$ to \texttt{key.pqcs/$v$/data.enc}
\State commit: write $(\mathit{ctx},C,\mathit{salt},p)$ to \texttt{key.pqcs/$v$/manifest.json}
\EndProcedure
\Procedure{Get}{$\mathit{key}, dk, \text{mode}$}
\State $v \gets$ newest version with a manifest; read and parse it
\State \textbf{reject} unless identity, mode, key id and $\mathrm{H}(C)$ all match
\State $S \gets \mathrm{ML\mbox{-}KEM.Decaps}(dk,C)$; \ $K \gets \mathrm{HKDF}(S,\mathit{salt},\dots)$
\For{each chunk $c_j$ of \texttt{data.enc}}
\State $M_j \gets \mathrm{AES\mbox{-}GCM}^{-1}_K(\dots)$; \ \textbf{reject} on failure
\EndFor
\State \textbf{reject} unless exactly $n$ chunks were read and the last is final
\EndProcedure
\end{algorithmic}
\end{algorithm}

\subsection{Bounded Sessions (Mode N1)}\label{sec:n1design}
In N1 one encapsulation yields a root $S_r$, and object $i$ of the session uses
\[K_i=\mathrm{HKDF}(S_r,\mathit{salt}_i,\text{``pqc-s3-session-v1''}\|0\|\mathit{ctx}_i),\]
with the session identifier, the object's sequence number and the bound authenticated in $\mathit{ctx}_i$.
Every object still stores the session's ML-KEM ciphertext, so it can be decrypted alone. A root
protects at most $B$ objects and lives at most $T_{\max}$ seconds. In the queue-aware variant,
\[B_t=\mathrm{clip}\bigl(B_{\min},B_{\max},\mathrm{round}(B_{\min}+(B_{\max}-B_{\min})\hat\rho)\bigr),\]
where
$\hat\rho$ is an exponentially weighted moving average ($\alpha=0.2$) of the fraction of a client process's worker threads with a request in flight: under light load a root is used for fewer
objects. $B_t$ is fixed per session, so $B_{\max}$ and $T_{\max}$ are hard caps. A leaked root
exposes at most $B_{\max}$ objects; compromise of the recipient's decapsulation key exposes all
objects in both P1 and N1. Receivers cache decapsulated roots under their own caps and reject
objects whose authenticated sequence number exceeds them.

\subsection{Cryptographic Core}
ML-KEM-768 comes from liboqs~\LiboqsVersion{} through liboqs-python~\LiboqsPyVersion{}
\cite{liboqs,liboqspython}. We build liboqs from a pinned release with only the ML-KEM parameter
sets enabled and load it from an explicit installation path, so the benchmark cannot silently pick up a different library; a start-up check verifies the library version and that ML-KEM-768 is enabled, and every call checks key and ciphertext sizes.
RSA-OAEP-4096 (SHA-256), X25519, HKDF and AES-256-GCM come from
pyca/cryptography~\CryptographyVersion{}~\cite{pyca}. A registry maps each mode to its
key-establishment and recovery functions, and the envelope module turns the result into a
streaming chunk encryptor or decryptor, so the storage code never holds a whole object. Before
any timed operation every worker process runs a warm-up that loads the libraries, performs a key generation, encapsulation, decapsulation, derivation and encryption round trip, and one full round trip in the mode under test, so that one-off costs never enter a timer.
An interoperability test checks ML-KEM in both directions against an independent implementation
(OpenSSL through pyca), and the manifest parser rejects unknown or missing fields, wrong types, inconsistent sizes and a key-establishment ciphertext that does not match its hash.

\subsection{Storage Layer}
The storage layer implements the commit protocol of Algorithm~\ref{alg:putget} on the MinIO
Python SDK~\MinioPyVersion. Ciphertext records are passed to the SDK through a file-like adapter
over the encryptor's output, so an object is uploaded in 8\,MiB parts while it is being encrypted;
on GET the stream is decrypted chunk by chunk into a sink. For benchmarking, the HTTP client uses a connection pool sized to the worker threads and performs no automatic retries, so failures are counted rather
than hidden inside latency. Auxiliary functions list committed versions, verify a commit by reading
it back, delete versions and collect uncommitted data left behind by interrupted uploads.

\subsection{Measurement Harness}
A \emph{run} executes one configuration (mode, operation, object size, concurrency and loop type)
with freshly started worker processes; it is the unit of replication. Concurrency $N$ is realized
as exactly $N$ worker threads spread over $\min(N,16)$ processes, one per vCPU. Each process warms
up, reports readiness, and all of them start at a common wall-clock instant, so that no worker
measures while others are still starting. Each run has a 5\,s warm-up phase and a 20\,s measured
phase; Python's garbage collector is run before and disabled during the timed window, so its
pauses cannot land inside a stage timer. In closed-loop runs each thread issues requests back to
back. In open-loop runs each process draws Poisson arrivals at its share of the target rate, a
request waits in a queue for a free thread, and the wait is recorded separately; a request that
cannot start before the end of the run is recorded as a failure, never dropped. GET runs read a
set of pre-written fixture objects that are created before and deleted after the run, and every
object written by a PUT run is deleted afterwards, outside the timed window.

Every request, including warm-up requests and failures, produces one record with
\texttt{perf\_counter} timers for the five stages of Algorithm~\ref{alg:putget}---key
establishment, key derivation, AES-GCM, manifest handling and storage---its total latency, the
thread CPU time it consumed, bytes on the wire and metadata size, plus identifiers that tie it to
its run, repetition, code commit and configuration. A client sampler records the CPU time and
resident memory of the worker processes and the host's CPU and network counters once per second;
a server sampler reads the same information from MinIO's Prometheus metrics endpoint.

\subsection{Validation}
A validator checks every data set before analysis and refuses it if any check fails: checksums of
all files; a complete schema with correct types for every record; that no request's stage times
exceed its total; that per run the 99th percentile of unaccounted time stays below 2\,\% of the
request time and below 1\,\% in aggregate; and that no N1 session exceeds its bound. The
\TestCount{} automated tests cover the cryptographic core, the commit protocol, tampering (bit flips; deleted, reordered, duplicated, truncated or extended chunks; swapped, replayed or relabelled manifests; mode downgrade), that manifests contain no secret material and private-key files are protected, session bounds under concurrent stress, and
end-to-end runs against a live MinIO.

\subsection{Testbed Automation}
A single script provisions and operates the cloud testbed: it creates both instances in one
cluster placement group with a firewall that admits SSH only from the operator's address, copies
the committed code, builds MinIO from source into a Docker image, formats the server's local NVMe
disk at boot, runs network (iperf3, ping) and disk (fio) baselines, starts experiments in a
detached session, fetches results and stops or deletes all resources. Before launch, a planner
estimates the run time and cost of each experiment configuration. To bound cost, both instances
stop themselves when idle, and the client stops itself shortly after an experiment completes.

\subsection{Analysis Pipeline}
Analysis is a three-stage pipeline. A summarizer streams the compressed request records of each
experiment once and writes one row per run (latency percentiles, stage means, throughput, CPU,
memory and session statistics). A statistics stage computes intervals, paired comparisons,
bottleneck labels and the queueing model. A final stage generates every figure, table and number
in this paper as \LaTeX{} macros, so no result is typed by hand.

\section{Experimental Methodology}\label{sec:method}
\subsection{Testbed}
The client runs on a \ClientType{} instance (\ClientCPU, \ClientVCPU{} vCPU, \ClientRAMGiB\,GiB)
and MinIO, as a single node in Docker with host networking, on an \ServerType{} instance (16
vCPU, local NVMe), both in one cluster placement group in AWS region \Region. Before the runs we
measured \LinkGbit\,Gbit/s (\LinkMiB\,MiB/s) between the hosts with iperf3, a \RTTms\,ms round
trip, and \FioReadMiB\,MiB/s read and \FioWriteMiB\,MiB/s write on the MinIO disk with fio. The
experiments ran code at commits \Commits.

\subsection{Workload}
PUT and GET are measured separately, mostly in a closed loop (each worker issues its next request
when the previous one completes). Concurrency 1--500 is measured at 64\,KiB and 1\,MiB; 16\,MiB
stops at 128 workers because 500 objects of 16\,MiB in flight exceed the client's memory; object
size 1\,KiB--500\,MiB is measured at one worker, with 128\,MiB at 32 and 500\,MiB at 16 workers.
Large objects require at least 10 measured operations per run. For RQ3, an open-loop generator
offers Poisson arrivals of 1\,KiB and 64\,KiB PUTs, served by 256 threads, at rates around the
measured capacity. N1 is measured at $B_{\max}\in\{10,100,1000\}$, $T_{\max}=60$\,s, and the
queue-aware variant at $B_{\min}=1$, $B_{\max}=100$.

\subsection{Metrics}
We report the four metrics of the study and one derived metric:
\begin{itemize}
\item \emph{Handshake overhead}: the time spent in key establishment per request (encapsulation,
RSA unwrapping, Diffie--Hellman or decapsulation), from the stage timers.
\item \emph{Throughput}: successful requests, or MiB, per second of the measured window.
\item \emph{CPU utilization}: CPU of the client's benchmark processes and of MinIO as a percentage
of each host's 16 vCPU during the measured window, and the client thread CPU time per request.
\item \emph{Memory growth}: peak resident memory over the run and its growth from the first
sample, for the client processes and for MinIO.
\item \emph{Response time} (open loop): queue wait plus service time per request.
\end{itemize}

\subsection{Replication and Statistics}
Every configuration runs five times, and the order of modes is shuffled within each repetition. A
run is the unit of analysis: we report the mean over runs with a Student-$t$ 95\,\% interval.
Modes are compared only within one batch, paired by repetition, as the ratio
$\exp(\overline{\log(x_a/x_b)})$ with a $t$-interval; a comparison is \emph{equivalent} if its whole
interval lies within $\pm$5\,\%, \emph{different} if it lies entirely outside, and
\emph{inconclusive} otherwise. Above one worker, stage timers include time spent waiting for the
Python interpreter lock, so we report key-establishment cost and stage shares at one worker and
client CPU as thread CPU time per request.

\subsection{Batches}
The study ran in four batches (Table~\ref{tab:sources}). In batches A--C the pause between runs,
meant to wait until MinIO stopped writing, fell back to 5\,s because MinIO in Docker does not
export its disk-write counter. A PUT run that followed another PUT run was then sometimes slowed by
\StallSlowMin--\StallSlowMax\,\%, consistent with the previous run's writeback and object purge
still in progress: \NoisySmallPutABC{} small-object PUT cells exceeded our 5\,\% limit on run-to-run
variation and \StallsABC{} runs were flagged as stalls. Because mode order was shuffled, this added
noise but no bias. Batch D re-measured all PUT cells up to 64\,KiB with a 40\,s pause, covering the
kernel's 30\,s dirty-page writeback and MinIO's 5\,s cleanup interval: the variation of P1 at
64\,KiB and 128 workers fell from \CVBeforePone\,\% to \CVAfterPone\,\% (B1: \CVBeforeBone\,\% to
\CVAfterBone\,\%), with \StallsD{} stalls in \RunsD{} runs. Batch D is the result of record for

\subsection{Bounded Session Amortization}
With a bound $B_{\max}$, N1 performed one ML-KEM operation per $B_{\max}$ objects
(\NoneKemPerReqHundred{} per request at $B_{\max}=100$), as designed and as the validator checked

\NoneSaveOneMin--\NoneSaveOneMax\,\textmu s of client CPU per request against P1, matching the

workers the saving grows to \NoneSaveConcMin--\NoneSaveConcMax\,\textmu s, because each ML-KEM
call through the Python binding costs more CPU under contention. All these intervals exclude
zero. Because ML-KEM is a small part of every request, this is visible as throughput only where
the client CPU is the bottleneck: small GETs at 32--128 workers (client CPU
\NoneGetClientPct\,\%) run \NoneGetGainMin--\NoneGetGainMax\,\% faster. On PUT, where MinIO limits
throughput, N1 is equivalent to P1 in \NonePutEquiv{} of \NonePutCells{} cells and inconclusive in
the rest. The queue-aware variant adapts as intended: under open-loop load of \QaRateLow{} and

requests/s at 1\,KiB, \QMidCap{} at 64\,KiB). We model the system as M/M/c with $c=\mu S_0$
servers, where $S_0$ is the service time at light load (\QSmallSzero\,ms; $c=\QSmallServers$ at

\QSmallStableErrPct--\QMidStableErrPct\,\% of the measurements. It misses the knee: at 1\,KiB and
\QSmallKneeRate{} requests/s ($\rho=\QSmallKneeHi$) it predicts \QSmallPredKnee\,ms while the
system was already unstable, with mean response above \QSmallMeasKnee\,ms; at 64\,KiB the same

\section{Discussion}\label{sec:discussion}
\textbf{Implications for migration.} For per-object envelope encryption on an S3-compatible store,
ML-KEM-768 is not a performance problem. Its key establishment costs tens of microseconds, less
than X25519 on PUT in our stack, and disappears against the milliseconds of storage round trips;
on every workload we measured, throughput is set by the network, by MinIO's write path or, for
small GETs, by the client CPU, and ML-KEM reaches those limits together with the classical modes.
Operators can therefore plan a migration around compatibility and key management rather than
capacity.

\textbf{Where the cost lies.} The measurable costs of migration are elsewhere: \ManifestExtraPone{}
more bytes of metadata per object than X25519, which matters for very small objects and for
object-count-based billing, and a few tens of microseconds of client CPU per request, which
matters only when the client is saturated. RSA-4096, in contrast, is a poor baseline to stay on:
its private-key operation makes small-object reads CPU-bound at \RoneGetThrMin--\RoneGetThrMax{}
of the throughput of ML-KEM.

\textbf{When to amortize.} Session amortization is useful exactly where the client CPU is the
bottleneck, such as many small reads from a few clients; elsewhere it trades compromise scope for
no measurable gain, and per-object ML-KEM is the simpler and safer default.

\textbf{Capacity planning.} The open-loop results matter more than any cryptographic choice:
response time collapses well before nominal saturation, so provisioning should target the knee
rather than the peak throughput.

\section{Threats to Validity}\label{sec:threats}
\textbf{Internal validity.} The pause between runs failed in batches A--C (Section~\ref{sec:method});
batch D repeated the affected cells with a working pause, but \NoisyD{} of its \CellsD{} cells
still exceed 5\,\% variation. Absolute small-object throughput differed by up to
\BatchDriftPct\,\% between batches, so all comparisons are within one batch. Stage timers above
one worker include interpreter-lock waiting. Five repetitions give $t$-intervals with four degrees
of freedom; the attribution of the small-PUT limit to MinIO's write path is by elimination, and
the AES-GCM cost difference between modes at 1\,MiB is unexplained.

\textbf{External validity.} The client is Python, so absolute costs include interpreter overhead
and differ from native or hardware-accelerated implementations; MinIO ran as a single node without
erasure coding; results describe one instance pair in one region. liboqs is intended for
prototyping, not production.

\textbf{Construct validity.} ``Handshake overhead'' is per-object key establishment, not a network
handshake; transport security was held constant.

\section{Conclusion and Future Work}\label{sec:conclusion}
We designed, implemented and validated an instrumented, reproducible benchmark of post-quantum
envelope encryption for S3-compatible object storage and measured it from 1 to 500 concurrent
workers and from 1\,KiB to 500\,MiB objects on two separate cloud instances. ML-KEM-768 adds
\HsPutPone--\HsGetPone\,ms per object, is statistically equivalent to X25519 within $\pm$5\,\% in
\HoneEquiv{} of \HoneCells{} comparisons, with none confirmed to differ by more, while RSA-4096
limits small-object reads to \RoneGetThrMin--\RoneGetThrMax{} of ML-KEM's throughput. Bounded
session amortization helps only when the client CPU is the bottleneck, and a queueing model with
load-independent service time does not predict where response time collapses.
Future work includes native and hardware-accelerated clients, distributed MinIO with erasure
coding across several servers, post-quantum signatures for object integrity, and a queueing model
with load-dependent service time.
