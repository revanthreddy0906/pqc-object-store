Data at rest that is encrypted under RSA or elliptic-curve keys can be recorded now and decrypted once a large quantum computer exists; public-key envelope encryption must move to ML-KEM, which places a key-encapsulation operation and its ciphertext on every object. It is known for primitives and for connection setup, but not on a concurrent object-store data path. We measured it on an S3-compatible store with a Python client on two architectures and a native Go reader, against X25519, RSA and two hybrid modes, using pre-registered paired equivalence tests and controls. With one unexplained exception in the native reader, ML-KEM changed throughput only at or near client CPU saturation, where the loss matched the extra client CPU per request: the Python client was 4.0 to 4.9% slower than with X25519. On the first architecture, a control with an equally large manifest attributes 17% of that deficit to ciphertext handling, and a control that reaches the same library through one foreign call, where the binding makes four, was equivalent to X25519 within 2%. A native reader saturated on one core was 9.5% slower, about half of which a slower key recovery in its library accounts for. The cost is a property of the implementation; what every implementation pays is storage: 1,056 more bytes of ciphertext per object than X25519. The results cover two clients, one single-node store and one cloud provider.
