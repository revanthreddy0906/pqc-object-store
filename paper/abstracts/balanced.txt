Data at rest that is encrypted under RSA or elliptic-curve keys can be recorded now and decrypted once a large quantum computer exists; public-key envelope encryption must therefore move to ML-KEM, which places a key-encapsulation operation and its ciphertext on every object. The cost of that operation is known for isolated primitives and for connection setup, but not on a concurrent object-store data path. We measured it on an S3-compatible store with a Python client on two processor architectures and a native Go reader, comparing ML-KEM with X25519, RSA and two hybrid modes in an exploratory campaign, a pre-registered confirmatory campaign with paired equivalence tests, and pre-registered controls. With one unexplained exception in the native reader, ML-KEM changed throughput only where the client was at or near CPU saturation: there the Python client was 4.0 to 4.9% slower than with X25519. Two controls on the first architecture show that the deficit there is produced by the library binding, which makes four foreign calls per decapsulation; with one call, ML-KEM was equivalent to X25519 within 2%. A native reader saturated on one core was 9.5% slower, so the size of the cost belongs to the implementation and not to the algorithm. The cost that every implementation pays is storage: 1,056 more bytes of ciphertext per object than X25519. The results cover two clients, a single-node store and one cloud provider.
